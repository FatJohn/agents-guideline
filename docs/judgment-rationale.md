## §2 補充判準（改既有檢查／過濾／驗證規則）

以下原句因 2026-09-09 常駐格式瘦身移出（含 2026-09-06、2026-09-09 兩次升級寫入的說明性文字）：

> 「跑測試全綠」不算：測試只覆蓋你改的那條路，「舊版擋得住而新版放行」的案例沒有人寫過，全綠與什麼都沒驗到長得一樣。

> 事後補的基線量的是新版自己。

> **方向不同，證據不同**：上面那組證據只擋**收緊**時的誤叫。

> **放寬**時基線與正向語料照做（它們擋意外變化），但**不足以結案**——放寬的差異本來就是刻意的，基線只證明「沒有意外變化」，不證明「沒有新洞」。

> 放寬安全檢查**另必派 fresh-context 對抗性探測**（攻擊者視角：別名、參數遮蔽、`this`、模板字面值等改寫，派 general-purpose 依 `10-dispatch.md` §1），且判不出是否安全的輸入維持擋——「證明安全才放行」，不是「認得出危險才擋」。

> 「證明安全才放行」，不是「認得出危險才擋」——2026-09-09 lesson 明確標出的對照句（見 `<REPO>/rules/50-lessons.md` 或 `<REPO>/docs/lessons-archive.md` 對應條目）。

> 「順手動到既有檢查」不算全新。

## §7 程式碼是唯一事實來源，文件與註解只是參考

使用者原話（2026-09-09）：

> Single Source of Truth 就只有 Code，文件永遠都只是參考，這件事情一定要讓 AI 知道，而且最好反覆強調，因為只要 Code 跟文件產生衝突，最後在運作的東西還是 Code，不是文件。
> 寫 Markdown 根本不只是為了什麼 Spec、規格文件、開發流程而已，更重要的是把留在對話討論的東西存檔，讓 AI 知道「想補對這個專案的認知」時知道去哪裡看。
> 以及例如為什麼這個東西這樣設計、哪些地方不能亂動、過去踩過什麼坑、現在有哪些邊界條件、做決策時應該遵守什麼原則邊界，這些東西如果全部只停留在對話裡面，早晚都會被 Context 洗掉、壓縮掉、稀釋掉、提醒到痛不欲生。
> 不然今天跟 AI 講得再清楚，過幾十輪之後，早就歪到姥姥家了，我覺得用這個角度去想之後，反而才能真的好好 Focus 在 Spec 要寫什麼，然後也不會過度在思考要怎麼把 Code 完全完整同步翻譯成人話文件，這件事不如讓 AI 讀 Code 就好。
> 很多人都搞錯方向，變成多維護一份完整的 Code 翻譯文件。
