## 0. 一句話結論

多輪驗收本身不是問題，**把每一輪的驗收結論寫成新的可證偽散文**才是。
40 輪驗收產出 93 則達門檻發現，其中 81 則（87%）落在散文；而散文修正**不觸發任何機械閘門**，
所以它要不要再驗一輪，完全落在當下的人為判斷上——而那個判斷沒有任何判準可依（詳見 §4 假設 4）。

「驗收輪數」＝ body 裡 `## 驗收第 N 輪` 的**段落數**（`gh pr list --json number,body -q '.[]|"\(.number) \([.body|scan("## 驗收第")]|length)"'`）；
本檔全部使用這個量法。裸字串 `驗收第` 的出現次數會多算 body 內部互相引用的那幾處（#372 多 2、#373 多 1）。

「零程式碼」＝該 commit 的 diff 只動 `*.md` 或程式碼中的註解行，`code=0`
（量法：`git show --format= --unified=0 <sha>`，逐行判檔名與是否 `^\s*(//|/\*|\*)`）。

**#376 是對照組**：4 行程式碼、0 輪、0 發現。輪數跟著散文量走，不跟著風險走。

### 1.2 被修正的句子是誰寫的（`git show <base>:<檔>` 逐行比對）

對每個修正 commit，把它**刪掉**的每一行拿去該 PR 第一個 commit 的 parent（＝當時的 `main`）同檔比對：

| PR（該 PR 的全部修正 commit） | 被修正的行在 main 上找得到 | 是本 PR 前面幾輪新寫的 |
|---|---|---|
| #371 | 16 | 117 |
| #372 | 9 | 28 |
| #373 | 23 | 33 |
| #374 | 14 | 39 |
| #377 | 5 | 21 |
| #378 | 1 | 5 |
| #380 | 13 | 51 |
| **只取 29 個純散文 commit** | **27** | **110（80%）** |

量法（可重跑，`<base>` ＝該 PR 第一個 commit 的 parent）：

```bash
git show --format= --unified=0 <sha> \
  | awk '/^--- a\//{f=substr($0,7); next} /^\+\+\+/{next} /^-./{print f"\t"substr($0,2)}' \
  | while IFS=$'\t' read -r f line; do
      git show "<base>:$f" 2>/dev/null | grep -Fqx -- "$line" && echo main || echo delta
    done | sort | uniq -c
```

上表每一列是**該 PR 全部修正 commit 的加總**，所以重現時要對那幾個 sha 各跑一次再相加。
例：#378 的三個修正 commit（`cdd30c45` 4 delta、`6f11b3c3` 1 delta、`7aee90f4` 1 main）＝表上的 1／5。
`<base>` 對 #378 是 `e24a9d32^`。

> **這個數字的已知偏差**：比對是逐行的，前一輪若把 main 上的句子**重新斷行**再改，
> 這個方法會把它算成「新寫的」。實查一例：#380 第 9 輪修的 `survey-sync.ts:230-231`，
> `git show fc2159cd^:packages/admin/src/api/survey-sync.ts` 顯示那句錯話在 main 上就存在
> （只是斷行位置不同），而腳本判成「新寫」。所以 80% 是**上界**；逐則的來源判定以第 2 節
> 每一列的「來源」欄為準（那一欄採 PR body 自帶的 `git show main:` 證據）。

### 1.3 這個習慣是什麼時候開始的

`gh pr list --limit 45` 掃 `驗收第`：

- #334–#369（2026-08-23 至 08-27）：**每一個都是 0**。

  兩個例外是 #353（只把一份文件標成快照）與 #376（4 行程式碼）。

兩個轉折點是分開的：**#351（08-24）每一輪的修正開始各自成為一個 commit**（之前是 amend 進同一個），
**#370（08-27）每一輪開始在 PR body 各寫一段**。記憶檔記載 #342（1 個 commit）當時跑了四輪驗收——
所以輪次早就存在，08-27 新增的是**把輪次寫下來**。

### 1.4 誰在讀這些 body

`gh pr view --json reviews`：這 8 個 PR 的 reviewer 只有兩個帳號——`FatJohn`（作者自己）與 `gemini-code-assist`。
沒有第三個人（#376 只有 `gemini-code-assist`）。`rg -n 驗收 docs/ CLAUDE.md AGENTS.md .gemini/` 在 portal 有不少命中
（review 紀錄、spec／plan 自帶的驗收條件等），但**沒有任何一條要求把驗收輪寫進 PR body**——
這是逐條讀過那些命中之後的結論，不是「零命中」；
`create-pr` skill 的內建骨架只有一段 `## Verification`（「只列實際執行過的指令與關鍵輸出」），
而且明文規定**選配段上限三段**（`skills/create-pr/SKILL.md:152`）、「篇幅隨變更規模縮放」（`:40`）。
所以這是純習慣，而且違反產生它的那個 skill 自己的規定。

> repo docs 內確實有 72 條指向本 repo PR 的連結（例如 `docs/architecture-review-admin-2026-08-23.md:411`
> 同時連向 #371 與 #372），所以「沒有人再打開這些 PR」是不成立的。那些連結引的是**決策出處**，
> 不是驗收軌跡；驗收軌跡在 commit message 裡已經有一份。取消 body 的驗收段落不會動到那 72 條連結指的東西。

## 4. 四個假設的裁決

### 假設 1：PR body 被當成驗收報告在寫 → **成立**

- 占發現的 19%（18 則落在 body；其中 13 則的產生器就是這個習慣本身，見 §3.3），且其中至少 6 則（#372 R4、#380 R2／R10、#373 R3、#374 R7、#378 R2）
  是**純轉述漂移**：repo 內的檔案是對的，錯的只有 body 裡的那份副本。
- 這個習慣有明確起點：`驗收第` 在 #334–#369 是 0 次，#370 起才出現。
- 沒有任何規則要求它。`create-pr` skill 的內建骨架只有一段 `## Verification`，
  而且明文「選配段上限三段」「篇幅隨變更規模縮放」「拿掉某段不會讓 reviewer 變慢就拿掉」。
- 讀者只有作者自己與 `gemini-code-assist`（`gh pr view --json reviews` 實查，八個 PR 皆然）。
  repo docs 內確實有 72 條指向本 repo PR 的連結（`rg -o --hidden 'web-pulse-portal/pull/[0-9]+' docs/ | wc -l`），
  所以「沒有人再打開這些 PR」不成立——但那些連結引的是**決策出處**，不是驗收軌跡。
- **價值 vs 成本**：它保存的軌跡在 commit message 裡已經有一份（`docs(schema): bound the claim in
  the rule's own file, not just its consumers` 這種標題本身就是該輪的結論），而 18/93（19%）的發現落在 body、
  其中 13 則的產生器就是這個習慣本身。

### 假設 2：規則疊加 → **成立為「疊加」，不成立為「矛盾」**

逐條讀過 `rules/20-judgment.md` §2/§4、`rules/10-dispatch.md` §5、`rubrics/document-quality.md`、
`rubrics/code-change.md`、portal `docs/implementation-quality.md` §1/§2/§4 與 `docs/code-review.md` DOC-1/DOC-2 之後，
**沒有找到任何一組「一邊要求 X、另一邊要求 non-X」**。使用者猜測的「全域規則與本地 repo 規則打架」不成立。

> 這是封閉式否定宣稱，射程限於上面列出的那幾份檔案與章節；沒有掃過 `skills/` 與各 repo 的 `.gemini/styleguide.md`。

真實的形狀是**四條各自合理的規則，加總起來要求每一個改動都附帶一大段可證偽散文**：

1. IQ 要求列出 owner／representations／consumers 與刻意 divergence 的理由與邊界 → 註解裡出現「這條規則的權威在哪、誰是消費端、為什麼不共用」。
2. EV 要求每個可證偽宣稱有指令輸出撐著 → 註解裡再出現現查指令、實測數字、證據等級。
3. GATE 要求「有機制擋著」的宣稱先查三件事 → 註解裡再出現「這道閘門擋得住什麼、擋不住什麼」。
4. DOC-1 禁止用歷史敘述帶過 → 每次 owner 一動，上述三類句子都必須**重寫**而不是加註。

四者的交集是：**每次把一條規則收成單一 owner，就會生出一段講「這條規則是什麼、誰讀它、它的證據到哪為止」的散文，
而那段散文本身沒有任何機械閘門守著。** 這就是為什麼九道閘門第一輪全過、而十輪的發現全在散文。

唯一一組真正的張力是 IQ §4「達成後停止，不順手整理無關程式」對上 `10-dispatch.md` §5
「這類驗收一定要問同一個錯誤還有沒有第二個現場」。實務上以「登記但不修」化解，成本約 4 則。

### 假設 3：verifier prompt 讓輪次無法收斂 → **大部分不成立**

- 「找同型第二現場」只產生 5/93（5%）的發現，而且多數被登記而非施作。
  它們也不是雞毛蒜皮：#373 第 5 輪的第六個現場、#380 第 5 輪的三處既有宣稱都被判定值得修。
  **這條的成本被高估了。**
- 真正在驅動輪次的是 `agents/verifier.md` 規則 4：「一律額外檢查：規則互相矛盾；
  檔案路徑／指令／工具名／章節引用是否真實存在；後續讀者會誤讀的模糊語句」——
  這是對**每一句話**的常設稽核義務。它本身是對的，問題在於它作用的對象每一輪都在變大。
- 「不接受空手回報」的效果在資料上看得到：40 輪裡只有 3 輪由驗收自己判定收斂（#373 R5、#377 R5、#378 R3）。
  #378 R3 另外還有作者判定的那一半（那一輪仍有一則發現，修完之後作者用一條 `rg` 直接判，沒有再派）。

### 假設 4：缺終止條件 → **成立，而且形狀比預期精確**

`rg` 掃過 `rules/`、`rubrics/`、`agents/`：**沒有任何一條規則在講什麼時候可以停止驗收迴圈。**

- `20-judgment.md` §2 補充判準（修正是新的未驗證改動，要對 delta 重新派一次驗收）**只有啟動端，沒有終止端**。
- §4「什麼訊號代表方向錯了」講的是換路，不是停驗。
- IQ §4「達成後停止」講的是範圍，不是輪次。

實際觀察到的停止方式有兩種，都不是規則寫的：

1. **驗收自己判定收斂**——40 輪裡 3 次，body 逐字：#373 R5「驗收判定已收斂，不值得再開一輪」、
   #377 R5「判定已收斂」、#378 R3「七條全 PASS，判定已收斂」。
2. **作者判定這一輪的改動用一條指令就判得出來，不再派**——#378 R3（改的是單一識別字，用 `rg` 判）、
   #380 R10（只改 body 的一句計數，用一條 `awk` 判）。

所以「純散文修正必然再來一輪」是**錯的**：`7aee90f4`（#378 R3，純註解）與 `b6c62e1e`（#377 R5，純註解）
都沒有觸發下一輪。準確的說法是：**純散文修正沒有任何機械閘門會對它出聲，所以它要不要再驗，
