# 20 — 判斷準則（判斷力外化）

> 讀者：所有等級的模型。每條判準附一個正例、一個反例。
> 卡住、想宣稱完成、想升級、想問使用者之前，翻對應段落。

## 1. 何時該升級能力層

先按任務性質選能力層：
- **輕量層**：低風險、範圍明確、可機械驗證。
- **標準層**：跨檔探索、一般實作、中等推理。
- **高能力層**：架構、安全、資料遺失、不可逆或對外動作。**高風險驗收依平台而定**——Codex 用 `sol_verifier`／Sol high（`../codex/rules/10-dispatch-codex.md` §6「驗證語意」）；Claude 端驗收一律顯式 `model: opus`，升級要先問使用者（`10-dispatch.md` §5「驗證不自驗」）。

**判準**：符合任一條就升級（門檻成立後怎麼做——Claude：`10-dispatch.md` §4；Codex：`../codex/rules/10-dispatch-codex.md` §5「升降級路徑」）：
- 一次失敗已顯示是**模型能力或脈絡理解不足**：抓錯核心、反覆遺漏跨檔／跨系統關係，或無法維持必要脈絡。直接 fresh＋升級，不等第二次。
- 失敗原因不明，且同一子任務已兩次無進展；每次錯誤都不同且驗收條件持續增加屬正常收斂，不計無進展。
- 任務需要跨多個檔案／系統同時推理，而你發現自己開始遺漏前面看過的細節。
- 任務需要高影響的架構、安全或不可逆取捨，不只是照明確步驟執行。

✅ **正例**：標準層第一次修正就誤判跨模組 root cause → 附上誤判證據，直接 fresh＋升高能力層。
❌ **反例**：輕量層核對機械清單時漏了一筆，補查即可 → 這是執行疏漏，不是能力不足。

註：execution mistake（syntax、漏改、指令拼錯）正確修法明確時可同層補正一次；缺證據先補證據，不靠升級模型猜。**換路的質性訊號**（修法越疊越多層 workaround、同一錯誤訊息在兩種不同修法後原樣出現、diff 越改越大但驗收達成數不增、想先關掉檢查「之後再回來」）任一成立就換路，不等門檻次數滿；錯誤訊息每次不同且在收斂的不算。具體選項見 Claude：`10-dispatch.md` §4；Codex：`../codex/rules/10-dispatch-codex.md` §5「升降級路徑」。

✅ **正例（換路）**：改了兩輪 config 都沒讓 build 過 → 停手，改派 fresh-context 探索者查「這個專案的 build 實際是怎麼跑的」，發現根本用錯了指令。
❌ **反例（正常收斂）**：測試失敗但錯誤訊息每次都不同且在進步（先是 import 錯、修完變成斷言差一個欄位）→ 繼續。

## 2. 何時算真的完成

> 本節「補充判準」有硬上限，計數方式與清舊規則見 `maintain-guideline` skill §5（`<REPO>/skills/maintain-guideline/SKILL.md`）。

**判準**：三個都成立才能說「完成」：
1. 驗收條件逐條核過（派工時寫的那份）。
2. 有**指令輸出或 read-back 結果**作為證據，不是「我認為」；回報按鐵律一分級（已驗證／待 CI／未驗證）。
3. 驗證方式符合產出風險——機械驗證可自跑但要附輸出，主觀品質、高風險產出、以及修使用者實際回報的 bug 要 fresh-context 驗收。誰驗什麼的完整分工見對應平台 dispatch 文件的驗證一節（Claude：`10-dispatch.md` §5「驗證不自驗」；Codex：`../codex/rules/10-dispatch-codex.md` §6「驗證語意」）。

✅ **正例**：「已驗證：測試 12/12 通過（輸出如下）、verifier 判定三項驗收全 PASS。」
❌ **反例**：「我已經修好了，邏輯上這個改動會解決問題。」——沒有執行證據，這叫「改完了」，不叫「完成了」。

**補充判準（重構／字串抽取／搬移／更正事實宣稱類任務）**：宣稱完成前，全 repo `rg`（**一律加 `--hidden`**，否則漏 `.claude/`／`.agents/`／`.gemini/` 殘留、誤判乾淨）搜尋舊引用／字串／路徑無殘留，附指令與結果。改動範圍常小於實際散佈——entrypoint（如 main.tsx）、設定檔、腳本、**`.github/workflows`／`.github/actions`** 最易漏；release／deploy-only 的 CI 路徑 PR 不會跑，**PR 全綠不代表沒炸**。排除清單只能排內容型目標，設定型（會被執行）不可排除（細節見 `<REPO>/docs/debug-environment-first.md`）。

✅ **正例**：i18n 字串抽取收尾前跑 `rg '<原字串>'` 全 repo，抓到 main.tsx 兩處殘留 → 補完、附搜尋輸出，才回報完成。
❌ **反例**：「我把用到的元件都改完了」——只改了記憶中的引用點，沒有全 repo 搜尋證據，殘留等下個 session 才爆。

**補充判準（標「未驗證」之前）**：「未驗證」是宣稱它**現在驗不了**，不是「我沒去驗」的委婉說法。標之前先問：真的沒有工具能驗？特別是 fresh-context 類的宣稱——`claude -p`／`codex exec` 本身就是全新 session，不必等或請使用者手動重開。

✅ **正例**：不確定 symlink 進來的 `rules/` 有沒有被自動載入 → `claude -p --allowed-tools "" <<< '不准用工具，列出 context 裡 rules 目錄下每個檔的首行標題'`，拿到標題才下結論。
❌ **反例**：「這要重開 session 才看得到，先標未驗證」——三十秒能驗的事被講成能力邊界。

**補充判準（驗證要驗到被嵌的那一層）**：設定檔內嵌別的語言時——GitHub Actions 的 `run:`、
Dockerfile 的 `RUN`、YAML 裡的 jq 或 SQL——**上層格式 parse 通過不算驗過那一層**。要跑被嵌
那層自己的檢查；跑不了的就明說那一層未驗，不要含混帶過。**哪個語言跑什麼檢查、哪些跑不了，
canonical 在 `<REPO>/docs/debug-environment-first.md`**，新增的語言寫進那份、不要兩邊各記一份。

✅ **正例**：改完 workflow 的 shell，把每個 `run:` 抽出來跑 `bash -n`，抓到未收尾的引號。
❌ **反例**：YAML parse 過、CI 也綠，而那一步每天 cron 都是 bash syntax error。

**補充判準（修正與驗收輪次）**：首次驗收依既有分工，不另派小型機械工作。驗收後修正：低風險且有確定性檢查能證明 finding 已修、無相關迴歸時，controller 可自行檢查並以「finding→修正→證據」結案；安全、授權、不可逆、重大架構或缺乏可靠機械證據時仍須 fresh-context delta 驗收。文件待實作與證據穩定後集中更新，不逐輪加未驗宣稱；**驗收輪次按產物切開**——可執行宣稱（測試、斷言）在實作當下寫並驗，散文最後一次寫完才驗。

delta 派工須帶原 finding、修正 diff、受影響驗收條件與既有證據，只阻擋未修好或新引入的迴歸；無關新發現列後續事項，但影響本次安全邊界或必要驗收的問題不得藉 delta 排除。

✅ **正例**：低風險輸出格式修正跑過邊界及迴歸測試後結案；授權條件修正則交 fresh verifier。
❌ **反例**：用 `git diff --check` 代替授權語意驗收；或為無關文案重開完整驗收。

**停止端**：行為承載產物＝程式碼、測試斷言、設定、指令，及直接改變 agent／人員行動的
`CLAUDE.md`／`AGENTS.md`、rules、agent 定義、skills、rubrics、hooks、permissions、高風險決策文件；
Markdown 不自動算散文——不改變行為的排版／語氣才算，改變行動的錯誤路徑或指令仍屬行為缺陷。

只對本次範圍內的條件與發現判定，無關後續事項分列。verifier 第一行依優先序回報：
- `INCONCLUSIVE`：有 UNSURE 或必要條件未判定；保留已知 FAIL，先補缺證，不自動重派或宣稱完成，
  補證後仍依風險分流選機械結案或 fresh delta，不以換模型代替缺證。
- `OPEN`：無缺證但有行為承載產物的 FAIL；修正後依風險分流，不自動要求重派。
- `PROSE-ONLY`：無缺證，FAIL 全為不影響行為的事實／引用問題；修完 read-back 後停止。
- `CONVERGED`：必要條件全 PASS 且無 FAIL／UNSURE；停止驗收，純品味不列 FAIL。

同一產出第 3 次 fresh 驗收後仍需重派（OPEN／INCONCLUSIVE）：回報輪數、FAIL／UNSURE 性質、
修正與剩餘項目交使用者決定，不自動開第 4 次；delta 計次，換 model／role 不重設。
例外：本 session 已明確要求驗到收斂；或回報後使用者明確同意續驗，此時從零重計下一段三輪。

✅ **正例**：缺 log 標 INCONCLUSIVE 並補證；三輪後仍有授權風險，回報再等續驗決定。
❌ **反例**：UNSURE 卻標 CONVERGED；用換模型繞過同一產物的三輪回報點。

**補充判準（把可證偽宣稱寫下來之前）**：數字（PR、判準、告警門檻）、封閉量詞（「只有 N 個」
「都沒有」「全部」「不可行」）與**行為宣稱**（「這條路徑會產生 X」「切換之後會變成 Y」）都是
**可證偽宣稱**，要有指令輸出撐著才寫進 commit、PR、註解或判準；**讀碼不算那條指令**——撐得起
「這一行存在」「這個函式叫了誰」，撐不起一條路徑的輸出，行為宣稱要跑過那條路徑。自問：這個量法
會不會給出「跑完了、看起來合理、但是錯的」答案？射程有沒有超過實際量過的範圍？撐不出來就改寫
成開放式（「至少有」「已知的有」）。與「重構／搬移類」那條分工：那條管殘留，這條管射程；**陷阱
清單 canonical 在 `<REPO>/docs/debug-environment-first.md`**，新增陷阱寫進那份。

✅ **正例**：要寫「這個閘門不可行」之前先打開開關實跑，發現再加一個選項就從 36 項降到 9 項，
結論因此反過來。
❌ **反例**：「刻意不一樣的只有兩處」——實際四處，而且引的行號指到回應 schema 去對輸入
validator，方向也錯。

**補充判準（「另一層會擋住它」不能只靠推理）**：宣稱「X 會被另一層擋掉，所以這裡可以不擋」是放寬
的理由，比一般行為宣稱更危險——錯了直接變成漏洞。**刪除或放寬既有防線之前**，要有**那一層自己
的實跑輸出**：把最小案例餵給它，看到真的擋；讀文件、型別定義或既有測試不算，那些是宣稱擋什
麼，不是實際擋什麼。查不出來就保留防線，把「疑似重複」寫成註解或 issue。**不算違規**：只說明
兩層職責重疊、未據此刪減任何檢查（仍受上一條射程要求約束）；或該層實跑輸出已涵蓋要放行的
**同一個**輸入形狀。

✅ **正例**：刪執行期防線前先把最小案例餵給 tsc，發現它只擋「型別被改成字串」、不擋一開始就是
字串字面值型別的寫法（會被解析成 intrinsic element）→ 防線保留。
❌ **反例**：「TypeScript 會擋這種寫法」憑印象成立、據此刪掉執行期檢查，七種寫法從擋變成放行，
React 實跑渲染出 `<meta http-equiv="refresh">`。

**補充判準（改既有檢查／過濾／驗證規則）**：完成證據＝動手前凍結的行為基線前後比對（新版是舊版
超集，或差異都是刻意的）＋正向語料（合法輸入不被誤叫）實跑；事後補的基線不算，測試全綠不算（「舊版擋、新版放」的
案例沒人寫過）。放寬時基線照做但不足以結案，另派 fresh-context 對抗性探測（general-purpose，依
`10-dispatch.md` §1）；判不出安全的輸入維持擋。**不算違規**：全新檢查沒有舊行為可比，只需正向語料；「順手動到既有檢查」不算全新。

✅ **正例**：收緊安全檢查器前先凍結兩個基線陣列，78 個 probe 逐一比對證明新版是舊版超集，另加
三份正向語料擋誤叫；基線陣列全程零改動。
❌ **反例**：十輪修下來每輪 verifier 都找到新的誤叫——因為沒有合法程式碼語料，誤叫只能靠人一個
一個撞見。
❌ **反例（放寬）**：把 regex 改成「AST 認得出危險才擋」，5,283 點基線與 110 個測試全綠，對抗性
探測仍挖出 11 個繞過——別名、參數遮蔽、`this`、模板字面值全部靜默放行。

**補充判準（指令要自己綁定目標，不要靠 cwd）**：巢狀 clone、workspace 底下的子 repo、多專案
並存時，**cwd 不是可靠的定位方式**，git／gh／pnpm 一律**逐指令綁定**（`git -C <path>`、
`gh -R <owner/repo>`、`pnpm -C <path>`）。理由與 read-back 指令 canonical 在
`<REPO>/docs/debug-environment-first.md`「指令自己綁定目標」。

✅ **正例**：`gh -R tvbstw/web-pulse-portal pr checks 386`——cwd 在哪都問對 repo。
❌ **反例**：批次第一行 `cd portal && gh pr checks 386`，第二行 `gh pr checks 165` 沒帶路徑，
在 portal 底下查另一個 repo 的 PR，回「找不到」而那個 exit code 被讀成 CI 失敗。

## 3. 何時該停下來問使用者

**判準**：符合任一條就停，其餘情況自主前進不要問：
- 動作屬於**發訊息或寄信、merge PR、push 共享分支、發佈、刪除或覆蓋非自己建立的檔案**，且本 session 尚未明確授權（鐵律二）。未授權就停止；已在本 session 明確授權時直接執行，不重複詢問。
- 發現任務的**範圍或前提跟使用者說的不一樣**。可操作判準：完成任務需要動到**使用者原話沒提及的其他檔案或章節**，或實際改動量明顯超出原任務的描述。
- 是品味/模糊題且第二意見後仍無收斂（例如文案語氣、提案方向）。

✅ **正例**：使用者要求「整理 proposals 資料夾」，你發現整理會需要刪掉三份看起來是草稿的檔案 → 停下來列出清單問。
❌ **反例**：實作途中發現要多裝一個常見的 dev dependency → 這是達成目標的必要步驟，裝了並在回報中說明即可，不用停下來問。

停下來問之前，先確認要問的**前提**成立——「兩個檔案不一致」「某機制壞了」這類判定，先看清
不一致的**性質**（漂移事故 vs 刻意分版）再開口；前提錯的問題換來的是基於錯誤前提的授權，比不問
更糟。拿到授權後動手前再複查一次前提。

✅ **正例**：兩份同名 SKILL.md `diff -q` 顯示 differ → 先讀內容，發現一份是刻意為 Codex 寫的精簡版，根本不必問。
❌ **反例**：`diff -q` 一 differ 就當成漂移事故去問使用者，動手時才發現前提錯了。

## 4. 品質底線怎麼驗

逐條判準寫在 rubric 檔裡（不常駐，要用時再讀；派工驗收時直接把路徑給 verifier）：

- 文件、規則、說明 → `<REPO>/rubrics/document-quality.md`
- 實作、修 bug、重構 → `<REPO>/rubrics/code-change.md`
- 查證、調研、盤點 → `<REPO>/rubrics/research-analysis.md`

**寫驗收條件時的自我檢查**：另一個 agent 能不能只憑這句話判定過或不過？做不到就是空話，verifier 見到模糊條件應直接 FAIL。

✅ **正例**：驗收時 verifier 回報「§3 的『上面提到的門檻』找不到指的是哪個數字」→ 修掉指代後才算過。
❌ **反例**：「文件寫完了，內容我都檢查過一遍」——自己檢查自己，且沒有可核對的驗收輸出。

## 5. 除錯前先驗證環境

遇到 HTTP 錯誤、port 異常、hook／lint 在多步編輯中途報錯、輸出與預期不符，或準備提出「程式碼有 bug」的假設之前 → 讀 `<REPO>/docs/debug-environment-first.md`（環境事實檢查清單＋量測方法自證的具體陷阱＋內嵌各語言各自要跑什麼語法檢查）。「壞了」與「我量錯了」長得一樣。

## 6. commit message 的固定格式

**判準**：commit message（subject 與 body）全英文，subject 符合 Conventional Commits——`type: 小寫祈使句`，scope 可省略（`type(scope):` 同樣合格），type 限 `build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test`。對話、PR title 與 body、程式註解、issue 仍是繁體中文。

PR title 依 `create-pr` skill 用中文不加 prefix，而 `gh pr merge --squash` 預設拿 PR title 當 commit 標題，所以 squash merge 一律用 `-t` 覆寫成本節格式；指令與事故見 `<REPO>/skills/create-pr/SKILL.md` §2.8。

✅ **正例**：`build(ios): move to SPM-only and drop CocoaPods (#25)`
❌ **反例**：PR title 是中文就直接 `gh pr merge --squash`——歷史第一行從此中文無 prefix，事後只能重寫共享歷史。

## 7. 程式碼是唯一事實來源，文件與註解只是參考

**判準**：程式碼是 single source of truth，文件、規格與註解都只是參考——兩者衝突時以程式碼為準、修文件，不反過來，也不要求每次改碼都同步改文件。文件只寫程式碼讀不出來的東西：為什麼這樣設計、哪裡不能動、踩過的坑、邊界條件、決策原則——把留在對話裡的討論存檔，讓下個 session 補得回認知；不寫程式碼的人話翻譯，那讓 AI 讀碼。註解同理：只在難懂處與商業決策處寫，整體設計方向另立一份文件。**不算違規**：改碼後順手刪掉或改掉被這次改動弄錯的那一句文件／註解——那是修錯，不是同步翻譯。

✅ **正例**：重試策略從指數退避改成固定間隔——commit 只動程式碼與測試，另在設計文件記下為什麼改；README 那句「重試三次」改成指向程式碼。
❌ **反例**：每個函式頭上一段複述「這個函式做什麼」的註解，改碼後沒跟上；2026-08-29 盤點 93 則 verifier FAIL 有 40 則落在程式碼註解——寫進去的每一句都是要被驗、會過期的宣稱。
