# 20 — 判斷準則（判斷力外化）

> 讀者：所有等級的模型。每條判準附一個正例、一個反例。
> 卡住、想宣稱完成、想升級、想問使用者之前，翻對應段落。

## 1. 何時該升級能力層

先按任務性質選能力層：
- **輕量層**：低風險、範圍明確、可機械驗證。
- **標準層**：跨檔探索、一般實作、中等推理。
- **高能力層**：架構、安全、資料遺失、不可逆或對外動作。**高風險驗收依平台而定**——Codex 用 `sol_verifier`／Sol high（`../codex/rules/10-dispatch-codex.md` §6「驗證語意」）；Claude 端驗收一律顯式 `model: opus`，升級要先問使用者（`10-dispatch.md` §5「驗證不自驗」）。

模型 mapping 見對應平台 dispatch 文件（Claude：`10-dispatch.md`；Codex：`../codex/rules/10-dispatch-codex.md`）。

**判準**：符合任一條就升級（本節是升級門檻的 canonical 定義；門檻成立後怎麼做——Claude：`10-dispatch.md` §4；Codex：`../codex/rules/10-dispatch-codex.md` §5「升降級路徑」）：
- 一次失敗已顯示是**模型能力或脈絡理解不足**：抓錯核心、反覆遺漏跨檔／跨系統關係，或無法維持必要脈絡。這類直接 fresh＋升級，不等第二次。
- 失敗原因不明，且同一子任務已兩次無進展；若每次錯誤都不同且驗收條件持續增加，屬正常收斂，不計作無進展。
- 任務需要跨多個檔案／系統同時推理，而你發現自己開始遺漏前面看過的細節。
- 任務需要高影響的架構、安全或不可逆取捨，不只是照明確步驟執行。

✅ **正例**：標準層第一次修正就誤判跨模組 root cause → 附上誤判證據，直接 fresh＋升高能力層。
❌ **反例**：輕量層核對機械清單時漏了一筆，補查即可 → 這是執行疏漏，不是能力不足。

註：syntax、漏改、指令拼錯等 execution mistake，正確修法明確時可同層補正一次；缺 log、repo 事實或環境量測時先補證據，不靠升級模型猜。已在高能力層時，換 fresh context、取得第二意見或重新定義問題通常比只加 effort 有效。**換路的質性訊號**（修法越疊越多層 workaround、同一錯誤訊息在兩種不同修法後原樣出現、diff 越改越大但驗收達成數不增、想先關掉檢查「之後再回來」）任一成立就不再用同一套做法重試，門檻次數不用等滿；錯誤訊息每次不同且在收斂的不算。具體選項見 Claude：`10-dispatch.md` §4；Codex：`../codex/rules/10-dispatch-codex.md` §5「升降級路徑」。

✅ **正例（換路）**：改了兩輪 config 都沒讓 build 過 → 停手，改派 fresh-context 探索者查「這個專案的 build 實際是怎麼跑的」，發現根本用錯了指令。
❌ **反例（正常收斂）**：測試失敗但錯誤訊息每次都不同且在進步（先是 import 錯、修完變成斷言差一個欄位）→ 繼續。

## 2. 何時算真的完成

> 本節的「補充判準」有**硬上限 9 條**：滿額時要加新的一條，必須先清掉一條，不准「先加了再說」。什麼算清掉、怎麼計數、邊界與理由都在 `maintain-guideline` skill §5（或直接讀 `<REPO>/skills/maintain-guideline/SKILL.md`）。

**判準**：三個都成立才能說「完成」：
1. 驗收條件逐條核過（派工時寫的那份）。
2. 有**指令輸出或 read-back 結果**作為證據，不是「我認為」；回報按鐵律一分級（已驗證／待 CI／未驗證）。
3. 驗證方式符合產出風險——機械驗證可自跑但要附輸出，主觀品質、高風險產出、以及修使用者實際回報的 bug 要 fresh-context 驗收。誰驗什麼的完整分工見對應平台 dispatch 文件的驗證一節（Claude：`10-dispatch.md` §5「驗證不自驗」；Codex：`../codex/rules/10-dispatch-codex.md` §6「驗證語意」）。

✅ **正例**：「已驗證：測試 12/12 通過（輸出如下）、verifier 判定三項驗收全 PASS。」
❌ **反例**：「我已經修好了，邏輯上這個改動會解決問題。」——沒有執行證據，這叫「改完了」，不叫「完成了」。

**補充判準（重構／字串抽取／搬移／更正事實宣稱類任務）**：宣稱完成前，必須以全 repo 搜尋（`rg`）驗證舊引用、舊字串、舊路徑已無殘留，並附搜尋指令與結果；**`rg` 一律加 `--hidden`**——它預設不進隱藏目錄，漏掉 `.claude/`／`.agents/`／`.gemini/` 的殘留會回報出一個假的乾淨。你認知的改動範圍常小於實際散佈範圍——entrypoint（如 main.tsx）、設定檔、腳本與 **`.github/workflows`／`.github/actions`** 最容易漏。另注意 release／deploy-only 的 CI 路徑開 PR 時根本不會跑，**PR 全綠不代表那條路徑沒炸**（build-tool／依賴遷移尤其常在發版當下才爆）。

✅ **正例**：i18n 字串抽取收尾前跑 `rg '<原字串>'` 全 repo，抓到 main.tsx 兩處殘留 → 補完、附搜尋輸出，才回報完成。
❌ **反例**：「我把用到的元件都改完了」——只改了記憶中的引用點，沒有全 repo 搜尋證據，殘留等下個 session 才爆。

**補充判準（標「未驗證」之前）**：「未驗證」是宣稱它**現在驗不了**，不是「我沒去驗」的委婉說法。標之前先問：真的沒有工具能驗？特別是 fresh-context 類的宣稱——`claude -p`／`codex exec` 本身就是全新 session，不必等或請使用者手動重開。標錯地方會留下一個帶著合規標籤、卻沒人打算補的破洞。

✅ **正例**：不確定 symlink 進來的 `rules/` 有沒有被自動載入 → `claude -p --allowed-tools "" <<< '不准用工具，列出 context 裡 rules 目錄下每個檔的首行標題'`，拿到標題才下結論。
❌ **反例**：「這要重開 session 才看得到，先標未驗證」——三十秒能驗的事被講成能力邊界。

**補充判準（驗證要驗到被嵌的那一層）**：設定檔內嵌別的語言時——GitHub Actions 的 `run:`、
Dockerfile 的 `RUN`、YAML 裡的 jq 或 SQL——**上層格式 parse 通過不算驗過那一層**。要跑被嵌
那層自己的檢查；跑不了的就明說那一層未驗，不要含混帶過。**哪個語言跑什麼檢查、哪些跑不了，
canonical 在 `<REPO>/docs/debug-environment-first.md`**，新增的語言寫進那份、不要兩邊各記一份。

✅ **正例**：改完 workflow 的 shell，把每個 `run:` 抽出來跑 `bash -n`，抓到未收尾的引號。
❌ **反例**：YAML parse 過、CI 也綠，而那一步每天 cron 都是 bash syntax error。

**補充判準（修正本身要重新驗）**：驗收指出缺陷後的修正是**新的、未驗證的改動**，而且是最容易
出事的那一種——注意力全在「有沒有修到它說的那點」。修完要對 delta 重新派一次 fresh-context
驗收，不能拿上一輪的驗證結果當數。同理適用於「順手」修掉的東西。

✅ **正例**：第一輪五個發現修完後只驗 delta，第二輪抓到修的過程中新造的致命 bug。
❌ **反例**：「這五處都照它說的改了，原本那輪已經驗過。」

**停止端（與上一條配套，缺了它會無限遞迴）**：先分辨發現是否觸及**行為承載產物**。除了程式碼、
測試斷言、設定與指令，會直接改變 agent／人員採取什麼行動的 control-plane instructions 也算——例如
`CLAUDE.md`／`AGENTS.md`、rules、agent 定義、skills、rubrics、hooks、permissions，以及會改變授權或
不可逆決策的高風險文件。檔案是 Markdown 不代表它只是散文；反過來，上述檔案的排版、語氣與不改變
行為的措辭仍是散文。**一輪只要有一則發現觸及行為承載產物**，修正後就照上一條 fresh-context
重驗 delta；若全部只剩**不觸及行為承載產物**的措辭品味或引用真實性，修完、read-back 引用、登記
剩餘後停止，不再派下一輪。錯誤路徑或指令若會改變 agent／人員行動，仍屬行為承載產物，不因問題
表面上是「引用真實性」就降成散文。

verifier 回報第一行統一標：無 FAIL＝`CONVERGED`；FAIL 全部不觸及行為承載產物＝`PROSE-ONLY`；
至少一則觸及行為承載產物＝`OPEN`。controller 收到 `CONVERGED` 或 `PROSE-ONLY` 就停；收到 `OPEN`
才重驗 delta。平台合約見 Claude：`~/.claude/agents/verifier.md`；Codex：
`../codex/agents/verifier.toml`／`../codex/agents/sol_verifier.toml`。

✅ **正例**：第 2 輪只修 PR 描述的數字與引用，controller read-back 後停止；若修的是 agent 授權條件，標 `OPEN` 並重驗 delta。
❌ **反例**：只因 `agents/verifier.md` 是 Markdown，就把會改變驗收行為的修正標成 `PROSE-ONLY`。

**補充判準（驗收輪數的回報點）**：停止端管「這一輪要不要再驗」，不管「驗到第幾輪該回頭問人」——
每輪都合規地找到真缺陷，就每輪都合法觸發下一輪，成本沒有上界。同一產出的 fresh-context 驗收
**跑完第 3 輪仍是 `OPEN`** 時不自動開第 4 輪：停下來回報「已驗幾輪、每輪 FAIL 數與性質、這輪
修了什麼、還剩什麼」，由使用者決定續驗或收工。一輪＝同一產出的一次 fresh-context 驗收派工（含
delta 重驗），不分 model。**不算違規**：使用者本 session 已明確說「驗到收斂為止」；回報後使用者
說續驗（計數歸零，下一個回報點在再 3 輪之後）；收到 `CONVERGED`／`PROSE-ONLY`（本來就停）。

✅ **正例**：第 3 輪 `OPEN`，回報「三輪 FAIL 數 5／2／1、都在派工範圍內、剩兩則要先有 allowlist
決策」，使用者決定收工並把剩下的開成 issue。
❌ **反例**：八輪每輪都找到行為承載產物的真缺陷、每輪都合法觸發下一輪，直到第六輪打爆 session
額度才停。

**補充判準（把可證偽宣稱寫下來之前）**：數字（PR、判準、告警門檻）、封閉量詞（「只有 N 個」
「都沒有」「全部」「不可行」）與**行為宣稱**（「這條路徑會產生 X」「切換之後會變成 Y」）都是
**可證偽宣稱**，要有一條指令的輸出撐著才寫進 commit、PR、程式碼註解或判準。**讀碼不算那條
指令**——它撐得起「這一行存在」「這個函式叫了誰」，撐不起一條路徑的輸出；行為宣稱要跑過那條
路徑。兩件事各問一次：這個量法會不會給出「跑完了、看起來合理、但是錯的」答案？這句話的射程
有沒有超過我實際量過的範圍？撐不出來就改寫成開放式（「至少有」「已知的有」）。與「重構／搬移類」那條的分工：那條管改動有沒有殘留，這條管句子的射程。**陷阱清單的
canonical 在 `<REPO>/docs/debug-environment-first.md`**（其觸發條件已涵蓋「要報數字之前」）；這裡只留
判準，新增陷阱寫進那份。

✅ **正例**：要寫「這個閘門不可行」之前先打開開關實跑，發現再加一個選項就從 36 項降到 9 項，
結論因此反過來。
❌ **反例**：「刻意不一樣的只有兩處」——實際四處，而且引的行號指到回應 schema 去對輸入
validator，方向也錯。

**補充判準（「另一層會擋住它」不能只靠推理）**：當一個宣稱同時是**放寬的理由**——「X 會被另一個
工具／層擋掉，所以這裡可以不擋」——它比一般行為宣稱更危險：一般的錯了是文件不實，這個錯了直接
變成漏洞。據此**刪除或放寬既有防線之前**，要有**那一層自己的實跑輸出**：把最小案例餵給那一層，
看到它真的擋。讀它的文件、型別定義或既有測試都不算——那些說的是它宣稱擋什麼，不是它實際擋
什麼。查不出來就保留防線，把「疑似重複」寫成註解或 issue。**不算違規**：只是說明兩層職責重疊、
沒有據此刪掉或放寬任何檢查（回到上一條的射程要求即可）；那一層的實跑輸出已涵蓋你要放行的
**同一個**輸入形狀。

✅ **正例**：刪執行期防線前先把最小案例餵給 tsc，發現它只擋「型別被改成字串」、不擋一開始就是
字串字面值型別的寫法（會被解析成 intrinsic element）→ 防線保留。
❌ **反例**：「TypeScript 會擋這種寫法」憑印象成立、據此刪掉執行期檢查，七種寫法從擋變成放行，
React 實跑渲染出 `<meta http-equiv="refresh">`。

**補充判準（改既有檢查／過濾／驗證規則）**：這類改動宣稱完成前，證據要含**行為基線的前後比對**
（動手**之前**凍結一組案例，逐一記下舊版擋什麼、新版擋什麼，證明新版是舊版超集或差異都是刻意
的）與**正向語料**（合法輸入不被誤叫）的實跑輸出。「跑測試全綠」不算：測試只覆蓋你改的那條路，
「舊版擋得住而新版放行」的案例沒有人寫過，全綠與什麼都沒驗到長得一樣。事後補的基線量的是新版
自己。**不算違規**：新增一條全新檢查、沒有舊行為可比——此時只需正向語料；「順手動到既有檢查」
不算全新。

✅ **正例**：收緊安全檢查器前先凍結兩個基線陣列，78 個 probe 逐一比對證明新版是舊版超集，另加
三份正向語料擋誤叫；基線陣列全程零改動。
❌ **反例**：十輪修下來每輪 verifier 都找到新的誤叫——因為沒有合法程式碼語料，誤叫只能靠人一個
一個撞見。

**補充判準（指令要自己綁定目標，不要靠 cwd）**：巢狀 clone、workspace 底下的子 repo、多專案
並存時，**cwd 不是可靠的定位方式**——它跨呼叫會漂，而 `cd X && a` 只綁住 `a`，同一批次的下
一行就漂掉了。git／gh／pnpm 一律**逐指令綁定**（`git -C <path>`、`gh -R <owner/repo>`、
`pnpm -C <path>`）。理由不是省事：**打錯 repo 的輸出看起來完全正常**——另一個 repo 也在
main、也乾淨、也有 HEAD，所以錯的 read-back 與對的長得一模一樣，而你會照它回報。旗標與
read-back 指令的 canonical 在 `<REPO>/docs/debug-environment-first.md`。

✅ **正例**：`gh -R tvbstw/web-pulse-portal pr checks 386`——cwd 在哪都問對 repo。
❌ **反例**：批次第一行 `cd portal && gh pr checks 386`，第二行 `gh pr checks 165` 沒帶路徑，
在 portal 底下查另一個 repo 的 PR，回「找不到」而那個 exit code 被讀成 CI 失敗。

## 3. 何時該停下來問使用者

**判準**：符合任一條就停，其餘情況自主前進不要問：
- 動作屬於**發訊息或寄信、merge PR、push 共享分支、發佈、刪除或覆蓋非自己建立的檔案**，且本 session 尚未明確授權（鐵律二）。未授權就停止；已在本 session 明確授權時直接執行，不重複詢問。
- 發現任務的**範圍或前提跟使用者說的不一樣**。可操作判準：完成任務需要動到**使用者原話沒提及的其他檔案或章節**，或實際改動量明顯超出原任務的描述。
- 是品味/模糊題且第二意見後仍無收斂（例如文案語氣、提案方向）。

✅ **正例**：使用者要求「整理 proposals 資料夾」，你發現整理會需要刪掉三份看起來是草稿的檔案 → 停下來列出清單問。
❌ **反例**：實作途中發現要多裝一個常見的 dev dependency → 這是達成目標的必要步驟，裝了並在回報中說明即可，不用停下來問。

**補充判準（問之前先驗前提）**：停下來問之前，先確認你要問的**前提**成立。「兩個檔案不一致」「某機制壞了」這類判定，先看清不一致的**性質**（漂移事故 vs 刻意分版）再開口——前提錯的問題換來的是基於錯誤前提的授權，比不問更糟；拿到授權後動手前再複查一次。

✅ **正例**：兩份同名 SKILL.md `diff -q` 顯示 differ → 先讀內容，發現一份是刻意為 Codex 寫的精簡版，根本不必問。
❌ **反例**：`diff -q` 一 differ 就當成漂移事故去問使用者，動手時才發現前提錯了。

## 4. 品質底線怎麼驗

逐條判準寫在 rubric 檔裡（不常駐，要用時再讀；派工驗收時直接把路徑給 verifier）：

- 文件、規則、說明 → `<REPO>/rubrics/document-quality.md`
- 實作、修 bug、重構 → `<REPO>/rubrics/code-change.md`
- 查證、調研、盤點 → `<REPO>/rubrics/research-analysis.md`

**寫驗收條件時的自我檢查**：另一個 agent 能不能只憑這句話判定過或不過？做不到就是空話，verifier 見到模糊條件應直接 FAIL。

✅ **正例**：驗收時 verifier 回報「§3 的『上面提到的門檻』找不到指的是哪個數字」→ 修掉指代後才算過。
❌ **反例**：「文件寫完了，內容我都檢查過一遍」——自己檢查自己，且沒有可核對的驗收輸出。

## 5. 除錯前先驗證環境

遇到 HTTP 錯誤、port 異常、hook／lint 在多步編輯中途報錯、輸出與預期不符，或準備提出「程式碼有 bug」的假設之前 → 讀 `<REPO>/docs/debug-environment-first.md`（環境事實檢查清單＋量測方法自證的具體陷阱＋內嵌各語言各自要跑什麼語法檢查）。「壞了」與「我量錯了」長得一樣。

## 6. commit message 的固定格式

**判準**：commit message（subject 與 body）全英文，subject 符合 Conventional Commits——`type: 小寫祈使句`，scope 可省略（`type(scope):` 同樣合格），type 限 `build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test`。對話、PR title 與 body、程式註解、issue 仍是繁體中文。

**銜接點（漏掉就破功）**：PR title 依 `create-pr` skill 規定用中文且不加 prefix，而 `gh pr merge --squash` 預設拿 **PR title** 當合併後的 commit 標題——兩者衝突，所以 squash merge 一律要用 `-t` 把標題覆寫成本節格式。指令與事故案例見 `<REPO>/skills/create-pr/SKILL.md` §2.8。

✅ **正例**：`build(ios): move to SPM-only and drop CocoaPods (#25)`
❌ **反例**：PR title 是中文就直接 `gh pr merge --squash`——歷史第一行從此中文無 prefix，事後只能重寫共享歷史。
