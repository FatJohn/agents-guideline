# 20 — 判斷準則（判斷力外化）

> 讀者：所有等級的模型。正反例與訂條理由在 `../docs/judgment-rationale.md` 對應標題下，用到才讀。
> 卡住、想宣稱完成、想升級、想問使用者之前，翻對應段落。

## 1. 何時該升級能力層

先按任務性質選能力層：
- **輕量層**：低風險、範圍明確、可機械驗證。
- **標準層**：跨檔探索、一般實作、中等推理。
- **高能力層**：架構、安全、資料遺失、不可逆或對外動作。高風險驗收見對應平台 dispatch 文件的驗證一節。

**判準**：符合任一條就升級：
- 一次失敗已顯示是**模型能力或脈絡理解不足**：抓錯核心、反覆遺漏跨檔／跨系統關係，或無法維持必要脈絡。直接 fresh＋升級，不等第二次。
- 失敗原因不明，且同一子任務已兩次無進展；每次錯誤都不同且驗收條件持續增加屬正常收斂，不計無進展。有機械指標（失敗測試數、錯誤數、benchmark 值）時改以數字判定：該輪未優於歷來最佳值（含改動前基線；沒跑到量測不算變好）就算一次無進展，錯誤訊息換了也一樣。
- 任務需要跨多個檔案／系統同時推理，而你發現自己開始遺漏前面看過的細節。
- 任務需要高影響的架構、安全或不可逆取捨，不只是照明確步驟執行。

註：execution mistake（syntax、漏改、指令拼錯）正確修法明確時可同層補正一次；缺證據先補證據，不靠升級模型猜。**換路的質性訊號**（修法越疊越多層 workaround、同一錯誤訊息在兩種不同修法後原樣出現、新 FAIL 與前一輪同根因只是換層或換形出現、diff 越改越大但驗收達成數不增、想先關掉檢查「之後再回來」）任一成立就換路，不等門檻次數滿；錯誤根因每次不同且在收斂的不算——看根因，不看訊息字面。每輪「照 plan 做了嗎」都 PASS 卻持續冒同根因的新症狀＝plan 缺陷，走重新定義問題，不換更強的執行者模型。具體選項見 Claude：`10-dispatch.md` §4；Codex：`../codex/rules/10-dispatch-codex.md` §5「升降級路徑」。

## 2. 何時算真的完成

**判準**：三個都成立才能說「完成」：
1. 驗收條件逐條核過（派工時寫的那份）。
2. 有**指令輸出或 read-back 結果**作為證據，不是「我認為」；回報按鐵律一分級（已驗證／待 CI／未驗證）。
3. 驗證方式符合產出風險——機械驗證可自跑但要附輸出，主觀品質、高風險產出、以及修使用者實際回報的 bug 要 fresh-context 驗收。誰驗什麼的完整分工見對應平台 dispatch 文件的驗證一節（Claude：`10-dispatch.md` §5「驗證不自驗」；Codex：`../codex/rules/10-dispatch-codex.md` §6「驗證語意」）。

**補充判準（重構／字串抽取／搬移／更正事實宣稱類任務）**：宣稱完成前，全 repo 搜尋舊引用／字串／路徑無殘留，附指令與結果。搜尋必須含隱藏目錄，否則漏 `.claude/`／`.agents/`／`.gemini/` 殘留、誤判乾淨：Bash 的 `rg` 一律加 `--hidden`（何時已是預設、Grep 工具差異見 `<REPO>/docs/install.md`「選配：擋主對話改 CI 設定的 hook 與 ripgrep 預設設定」）。改動範圍常小於實際散佈——entrypoint（如 main.tsx）、設定檔、腳本、**`.github/workflows`／`.github/actions`** 最易漏；release／deploy-only 的 CI 路徑 PR 不會跑，**PR 全綠不代表沒炸**。排除清單只能排內容型目標，設定型（會被執行）不可排除（細節見 `<REPO>/docs/debug-environment-first.md`）。

**補充判準（標「未驗證」之前）**：「未驗證」是宣稱它**現在驗不了**，不是「我沒去驗」的委婉說法。標之前先問：真的沒有工具能驗？特別是 fresh-context 類的宣稱——`claude -p`／`codex exec` 本身就是全新 session，不必等或請使用者手動重開。

**補充判準（驗證要驗到被嵌的那一層）**：設定檔內嵌別的語言時——GitHub Actions 的 `run:`、
Dockerfile 的 `RUN`、YAML 裡的 jq 或 SQL——**上層格式 parse 通過不算驗過那一層**。要跑被嵌
那層自己的檢查；跑不了的就明說那一層未驗，不要含混帶過。**哪個語言跑什麼檢查、哪些跑不了，
canonical 在 `<REPO>/docs/debug-environment-first.md`**，新增的語言寫進那份、不要兩邊各記一份。

**補充判準（修正與驗收輪次）**：首次驗收依既有分工，不另派小型機械工作。驗收後修正：低風險且有確定性檢查能證明 finding 已修、無相關迴歸時，controller 可自行檢查並以「finding→修正→證據」結案；安全、授權、不可逆、重大架構或缺乏可靠機械證據時仍須 fresh-context delta 驗收。文件待實作與證據穩定後集中更新，不逐輪加未驗宣稱；**驗收輪次按產物切開**——可執行宣稱（測試、斷言）在實作當下寫並驗，散文最後一次寫完才驗；同一交付批次中證據已穩定、無個別交付依賴的散文可合併成一次驗收，不得為合批延後已可交付的 issue／PR 或阻塞後續工作，行為承載文件不因此降成散文；平行批次的切片依 `<REPO>/skills/parallel-dispatch/SKILL.md` §5「VALIDATION：切片驗收」各自驗收、收斂即整合，不受此限。

delta 派工須帶原 finding、修正 diff、受影響的原始驗收條件與既有證據；evidence set 範圍、歸因與收斂判定的 canonical 在 `~/.claude/agents/verifier.md` 規則 4（Codex：`../codex/agents/verifier.toml`）。首輪 brief 指定 repo 外的探針落檔路徑，delta brief 附該路徑；除「改既有檢查」的放寬探測外，delta brief 不另指定新探測形狀或開放式找漏洞。修正者（含 controller 自修）對文件新寫或改寫的句子逐句對照權威來源，對新增或修改的測試斷言與守門檢查附實跑會變紅的突變紅／綠輸出（Claude 細節見 `~/.claude/agents/worker.md` 規則 2），兩者證據帶進 delta brief。

**停止端**：行為承載產物＝程式碼、測試斷言、設定、指令，及直接改變 agent／人員行動的
`CLAUDE.md`／`AGENTS.md`、rules、agent 定義、skills、rubrics、hooks、permissions、高風險決策文件；
Markdown 不自動算散文——不改變行為的排版／語氣才算，改變行動的錯誤路徑或指令仍屬行為缺陷。

只對本次範圍內的條件與發現判定，無關後續事項分列。verifier 第一行依優先序回報狀態並附下一步：
- `INCONCLUSIVE`：有 UNSURE 或必要條件未判定；保留已知 FAIL，先補缺證，不自動重派或宣稱完成，
  補證後仍依風險分流選機械結案或 fresh delta，不以換模型代替缺證。
- `OPEN`：無缺證但有行為承載產物的 FAIL；修正後依風險分流，不自動要求重派。
- `PROSE-ONLY`：無缺證，FAIL 全為不影響行為的事實／引用問題；修完 read-back 後停止。
- `CONVERGED`：必要條件全 PASS 且無 FAIL／UNSURE；停止驗收，純品味不列 FAIL。

同一產出第 3 次 fresh 驗收後仍需重派（OPEN／INCONCLUSIVE）：回報輪數、FAIL／UNSURE 性質、
修正與剩餘項目交使用者決定，不自動開第 4 次；delta 計次，換 model／role 不重設。
例外：本 session 已明確要求驗到收斂；或回報後使用者明確同意續驗，此時從零重計下一段三輪。

**補充判準（把可證偽宣稱寫下來之前）**：數字（PR、判準、告警門檻）、封閉量詞（「只有 N 個」
「都沒有」「全部」「不可行」）與**行為宣稱**（「這條路徑會產生 X」「切換之後會變成 Y」）都是
**可證偽宣稱**。對新增／變更且宣稱現況的內容，先映射同一 artifact 且仍有效的既有證據；一份證據可
批次支持多個宣稱，不逐句另跑，無映射才補指令。讀碼只證存在或呼叫關係，行為宣稱仍須實跑路徑；規格、
契約與驗收條件描述應有行為，未實現時保留並列缺口，不改弱。撐不起現況射程就改寫成開放式（「至少有」
「已知的有」）；長存文件引用優先用符號名或段落標題；驗收證據可用綁定版本的檔案:行號。**陷阱清單 canonical 在 `<REPO>/docs/debug-environment-first.md`**，新增陷阱寫進那份。

**補充判準（「另一層會擋住它」不能只靠推理）**：宣稱「X 會被另一層擋掉，所以這裡可以不擋」是放寬
的理由。**刪除或放寬既有防線之前**，要有**那一層自己
的實跑輸出**：把最小案例餵給它，看到真的擋；讀文件、型別定義或既有測試不算。查不出來就保留防線，把「疑似重複」寫成註解或 issue。**不算違規**：只說明
兩層職責重疊、未據此刪減任何檢查（仍受上一條射程要求約束）；或該層實跑輸出已涵蓋要放行的
**同一個**輸入形狀。

**補充判準（改既有檢查／過濾／驗證規則）**：完成證據＝動手前凍結的行為基線前後比對（新版是舊版
超集，或差異都是刻意的）＋正向語料（合法輸入不被誤叫）實跑；事後補的基線不算，測試全綠不算。放寬時基線照做但不足以結案，另派依平台 dispatch 路由的 fresh-context 對抗性探測（Claude：`10-dispatch.md` §5「驗證不自驗」；Codex：`../codex/rules/10-dispatch-codex.md` §6「驗證語意」）；判不出安全的輸入維持擋。**不算違規**：全新檢查沒有舊行為可比，只需正向語料；「順手動到既有檢查」不算全新。

**補充判準（指令要自己綁定目標，不要靠 cwd）**：巢狀 clone、workspace 底下的子 repo、多專案
並存時，**cwd 不是可靠的定位方式**，git／gh／pnpm 一律**逐指令綁定**（`git -C <path>`、
`gh -R <owner/repo>`、`pnpm -C <path>`）。理由與 read-back 指令 canonical 在
`<REPO>/docs/debug-environment-first.md`「指令自己綁定目標」。

## 3. 何時該停下來問使用者

**判準**：符合任一條就停，其餘情況自主前進不要問：
- 動作屬於**發訊息或寄信、merge PR、push 共享分支、發佈、刪除或覆蓋非自己建立的檔案**，且本 session 尚未明確授權（鐵律二）。未授權就停止；已在本 session 明確授權時直接執行，不重複詢問。
- 發現必須擴大**功能、契約、權限或外部影響**，而非只是在已授權 scope 內補齊必要實作檔與 dependency。前者停下確認；後者自主完成並在回報說明。
- 是品味/模糊題且第二意見後仍無收斂（例如文案語氣、提案方向）。
- 驗證或動作需要使用者**本人在場**（live 登入、實機操作、手動觸發）且會阻塞後續工作：先問可用時段再派，不要先派出去等；其餘已授權且不依賴使用者的工作照常繼續。

停下來問之前，先確認要問的**前提**成立——「兩個檔案不一致」「某機制壞了」這類判定，先看清
不一致的**性質**（漂移事故 vs 刻意分版）再開口。拿到授權後動手前再複查一次前提。

## 4. 品質底線怎麼驗

**寫驗收條件時的自我檢查**：另一個 agent 能不能只憑這句話判定過或不過？做不到就是空話，verifier 見到模糊條件應直接 FAIL。

## 5. 除錯前先驗證環境

遇到 HTTP 錯誤、port 異常、hook／lint 在多步編輯中途報錯、輸出與預期不符，或準備提出「程式碼有 bug」的假設之前 → 讀 `<REPO>/docs/debug-environment-first.md`（環境事實檢查清單＋量測方法自證的具體陷阱＋內嵌各語言各自要跑什麼語法檢查）。

## 6. commit message 的固定格式

**判準**：commit message（subject 與 body）全英文，subject 符合 Conventional Commits——`type: 小寫祈使句`，scope 可省略（`type(scope):` 同樣合格），type 限 `build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test`。對話、PR title 與 body、程式註解、issue 仍是繁體中文。

PR title 依 `create-pr` skill 用中文不加 prefix，而 `gh pr merge --squash` 預設拿 PR title 當 commit 標題，所以 squash merge 一律用 `-t` 覆寫成本節格式；指令與後果見 `<REPO>/skills/create-pr/SKILL.md` §2.8。

## 7. 現況證據與規格權威分工

**判準**：以已部署程式、設定與實跑確認現況；以核定需求、契約與驗收條件判斷應有行為。兩者不一致時先查明原因，不自動選擇修程式或修文件。文件只留業務意圖、重要邊界、決策理由與驗收例子，不逐段翻譯程式；行為／契約變更要更新受影響規格及驗收例子，純內部重構無須同步文件。失準註解仍要修正。
