# Rubric — review finding 的品質

> 讀者：被派去執行 `code-review` skill 的 fresh reviewer（Claude：`general-purpose`；Codex：`reviewer`），以及任何要在 PR 上留 review 留言的 agent。controller 收到 finding 決定修不修時也可對照。
> 用途：管「發出去的每一條 finding 本身站不站得住」。什麼時候派 reviewer、diff 要查什麼，在 `~/.claude/skills/dispatch/SKILL.md`（Codex：`<REPO>/global/codex/rules/dispatch.md`）與 `code-change.md`；本檔只管 finding 的形狀與發出前的查證。
> 來源：2026-08 對一組前端 repo 盤點 67 條 AI inline review：42 條採納、24 條婉拒，婉拒的 24 條裡 14 條是想像出來的 null／undefined；8 條標 HIGH 有 4 條被駁，MEDIUM 反而準。歸納出的通用判準在此；repo 專屬的規則 ID、lint 清單、嚴重度門檻留在各 repo 自己的 review 判準。
> 判定方式：reviewer 發每條 finding 前自查 §1–§3；controller 或 verifier 覆核 finding 時逐條判 PASS／FAIL，FAIL 附是哪條 finding、違反哪一款。

## 1. finding 合約

每條 finding 必備三項，缺一就不發：

- **具體失敗情境**：什麼輸入或狀態下會壞、壞成什麼樣。舉不出來的是偏好，不是 finding（§3 的 CRITICAL 例外：機密外洩、破壞資料、產物無法運作不需要失敗輸入，但要指出外洩或破壞的是什麼）。
- **具體修法**：短的直接給改法；長的描述做法。
- **查證依據**（§2）：讀了哪個檔的哪一行、哪個版本的文件或原始碼。

其他規範（管 reviewer 的做法，不是每條 finding 的欄位）：

- **不確定就寫成問句**（「這裡不檢查 X 是刻意的嗎？因為 Y」）並標明是待確認，不把猜測寫成斷言；問句型 finding 以「指出的不確定點具體到作者能直接回答」為過。
- **只 review 本次改動**：範圍是改動過的整段 code（`code-change.md` §3），不是 diff `^+` 的行；既有問題除非被這次改動直接放大，否則不順手翻出來。
- **同一問題多處只在第一處完整說明**，其餘引用該處；引用型 finding 以「引用處有完整三項」為過。
- **處理優先序**：正確性 → 安全 → repo 自己的編號規則 → 效能 → 其他。
- **repo 有自己的 review 判準時先讀**（`docs/code-review.md`、styleguide、`AGENTS.md` 的 review 小節等）；引用其規則 ID 前確認那條真的存在，沒有規則涵蓋的缺陷說明為什麼它是缺陷，不引用不存在的規則。

## 2. 斷言前先查證

歷來被婉拒的 finding 多數不是「規則沒寫」，是「沒查證就斷言」。

- **主張型別不合之前先把型別讀出來**：null／undefined、參數型別、overload 都算同一類。追不到 null 從哪裡進來就不要求防禦，也不要求為那個不存在的情境補測試；要求把一個值換成另一個值之前，確認那個簽名收得了。讀不出型別就不提。
- **主張某個 library 有某種行為之前，講出版本與文件或原始碼依據**；模型的記憶不是依據。
- **不主張某個版本「還不存在」**：訓練資料比 repo 舊。
- **不斷言某個檔案「沒被包含在這次改動裡」**：拿到的 diff 可能有限制。說「我看不到 X」，不說「作者漏了 X」。
- **熟悉的符號名不代表熟悉的來源**：同名的型別或函式可能來自本專案自己的模組，點進去看。
- **主張某段 code 違反 repo 慣例之前，先確認那條慣例真的寫在 repo 的判準裡**；寫不出出處的「慣例」是你的偏好。
- **repo 一致採用的 pattern 不是 finding**：想改慣例另開討論，不在單一 PR 的 review 裡提。
- **看起來像筆誤的字串先確認不是逐字引用**：佔位字串、錯誤訊息原文、外部 API 欄位名常常「看起來不對」。
- **主張「已被 lint／型別檢查／CI 擋住所以不提」或「沒有東西擋」之前**，照 `document-quality.md` §2 查三件事：rule 的 severity、閾值的實際數字、跑它的 script 有沒有讓 warning 變成失敗；同一 repo 不同目錄可能不一樣。

## 3. 嚴重度

- **CRITICAL**：會外洩機密、破壞資料，或讓已發布的產物無法運作。不要求失敗輸入，但要指出外洩或破壞的是什麼。
- **HIGH 只給舉得出失敗輸入的缺陷**：有明確的失敗輸入，且會產生錯誤結果或當掉。
- **MEDIUM**：契約類缺陷、版面破裂、相容性、可維護性上的實質問題。
- **LOW＝不發**：個人偏好、風格、「可以但不必」。**不為了讓建議出得去而拉高嚴重度**；repo 設了門檻（如 Gemini 的 `comment_severity_threshold`）時，低於門檻等於不發言，一樣不灌水。

## 4. 不要留言的事

這些不是「沒發現」，是已經處理掉或刻意如此；重提只製造噪音。

- **N-1 想像出來的 null／undefined**（§2 第一條）。
- **N-2 不可達分支的防禦**：已被上游條件、型別或 UI 狀態排除的情境不需要再夾一層。
- **N-3 把刻意的設計當缺陷**：共用元件的預設值、對齊規格的數值、仍在使用的 state。判多餘之前先找它的使用處。
- **N-4 已被 lint／型別檢查／CI 機械擋住的規則**（查法見 §2 末條）。例外：改動處**新加**的 `eslint-disable`、`@ts-ignore`、`# noqa` 這類抑制註解沒寫理由，要抓。
- **N-5 泛泛要求加測試**：「建議補測試」不指名情境等於沒說。要提就指名「哪個輸入、預期什麼結果」。
- **N-6 diff 摘要、行為中性的重寫、純風格偏好**。
- **N-7 版本不存在、檔案不在 diff 的主張**（§2）。
- **N-8 散文與註解裡的逐字引用**（§2）。

## 5. 與其他判準的分工

- `~/.claude/rules/judgment.md` 8「可證偽宣稱」管製作者自己寫下的宣稱；本檔 §2 是同一原則套在 reviewer 身上。
- `code-change.md` 管「diff 要查什麼」（執行證據、作假、殘留、失敗路徑）；本檔管「查出來的東西發出去前站不站得住」。
- `document-quality.md` §2 管文件裡「有機制擋著」的宣稱；本檔 §2 末條與 N-4 借用同一個查法。
