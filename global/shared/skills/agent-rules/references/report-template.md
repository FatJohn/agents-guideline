# 稽核報告範本

讀者：跑完 `agent-rules` 六步、要交報告的 session。報告的讀者是**沒讀過本 skill 的人**（專案維護者、team lead），所以報告不用 skill 的步驟名當章節，每個詞第一次出現就解釋，結論在前、證據在後。

## 三條硬規則

1. **主角是規則，不是程式碼。** 稽核對象是常駐檔與規則文件寫得對不對、agent 讀不讀得到；程式碼既有違規不是 finding。命中數只用來說「開了這個 lint 會咬到 N 處既有程式碼」，而且要註明那是規則建立前寫的、清不清零另案。
2. **每條建議寫因果。** 固定四行：改什麼、現在的問題、改法、改完避免什麼。少一行就不是建議，是觀察。
3. **讀者只讀「結論」與「建議修改」就能做決定。** 附錄是給想核對證據的人，正文不引用附錄的表格編號當理由。

## 結構

```markdown
# <專案> 規則稽核報告（<日期>，<branch> <短 SHA>）

## 結論

三到五句：規則現在放在哪、agent 什麼時候讀得到；最大的一個問題是什麼、會造成什麼；建議幾條、哪幾條要你決定。

## 建議修改

分三組，每組沒有內容就寫「無」。每條四行。

### 改常駐檔與規則文件

- **改什麼**：<檔案>:<行> 的規則「<標題>」
- **問題**：<agent 現在會怎樣：漏判、判不出、讀到兩份互相矛盾的來源>
- **改法**：<具體動作：改成「…」／刪掉／搬到…>
- **改完避免**：<什麼情境下的什麼錯>

### 改 lint 或 CI 設定

- **改什麼**：<lint 名稱或檢查指令>
- **問題**：<規則文件寫了要做 X，但沒有東西在擋，或設定把它關掉了>
- **改法**：<開 lint／加 CI 檢查／刪規則，二選一時兩個都列>
- **改完避免**：<同上>；開了會咬到 N 處既有程式碼（規則建立前寫的），清零或先設基線另案

### 改流程

- **改什麼**：<review brief、CI job、產生腳本>
- **問題**、**改法**、**改完避免**：同上

## 不用動的

已經做對、這次看過但不建議改的，一行一條，讓讀者知道範圍涵蓋到哪。

## 附錄 2：每條規則有沒有東西在擋

一句說明：每條規則分三類。「已擋」＝啟用中的 lint、編譯器或既有測試會抓到，規則文字可以刪；「可擋未擋」＝有現成 lint 或一行檢查能抓，但沒開或沒跑；「只能判斷」＝要讀上下文，留給人與 agent。

| 規則（來源:行） | 分類 | 證據 | 建議 |
|---|---|---|---|

兩個要特別點名的形狀：規則與 lint 設定互相矛盾（規則要、設定關）；lint 套件在依賴裡但執行它的 plugin 沒跑。

## 附錄 3：常駐檔逐行檢查

一句說明：agent 只憑常駐檔那一行判斷規則適不適用，所以每行要寫出觸發條件與做法。

| 規則 | 問題類型（觸發範圍比本文窄／只寫用哪個判準／只在一處有） | 改寫成 |
|---|---|---|

## 附錄 4：跑過的指令與輸出

每條證據可重跑。

## 交給 agent 執行

把要做的建議編號填進去，整段貼給任何 coding agent 就能開工。沒勾的建議不做。

    在 <repo> 執行規則稽核報告 <報告路徑> 的建議 <編號清單>，其餘建議不做。
    每條照報告的「改法」做，不擴大範圍；碰到報告沒寫的取捨先停下來問。
    授權：可改 <AGENTS.md／guideline／analysis_options.yaml／CI 腳本>，不 push、不開 PR。
    改完：重跑 <產生索引的指令> 與 <lint／測試指令>，附輸出；
    每條建議回報「改了什麼檔案:行、重跑指令的輸出、報告寫的『改完避免』現在怎麼驗」。
    驗收條件：<產生索引的 --check> exit 0；lint／測試全綠或只剩報告註明的既有命中；
    被刪的規則全 repo 搜尋不到殘留引用（含 reviewer 版本與手寫摘要）。
```

## 寫法檢查

交報告前自查：

- 「結論」裡沒有 A／B／C、「三層」、「brief」這些 skill 內部詞；用到就當場解釋。
- 「建議修改」每條四行齊全，且「改什麼」指向常駐檔、規則文件、lint 設定或流程，不指向某個 `.dart`／`.ts` 檔。
- 程式碼命中數只出現在「改完避免」的尾註或附錄。
- 讀者不翻附錄也能對每條建議說「改」或「不改」。
- 「交給 agent 執行」那段的授權行只列報告建議會碰到的檔案，驗收條件可機械判定。
