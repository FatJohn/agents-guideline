# Adapter：外部 CLI process（純 shell、tmux、VS Code／Cursor terminal、Herdr、Orca、未來工具）

配合 [../SKILL.md](../SKILL.md) §9 的 adapter 契約使用（launch、follow-up、query status、collect、stop、workspace）。這一類環境的共同點：**每個 worker 是一個獨立的 coding agent CLI process**（`claude`、`codex` 或其他），controller 是另一個 session 或人。tmux、VS Code、Herdr、Orca 只是這些 process 的 terminal／session 容器；它們提供的 workspace、分頁、狀態面板都是 UX，不進 SKILL 的任何判斷。未來工具只要能做下表五件事，就照本檔用，不必改 SKILL。

| 契約項目 | 本 adapter 的做法 |
|---|---|
| launch | 在該片 worktree 目錄啟動 CLI，brief 從檔案餵入：`cd <wt> && claude -p "$(cat <brief>)"`／`codex exec "$(cat <brief>)"`，或互動模式貼 brief。旗標以當下 `--help` 現查，不憑記憶。session 由容器決定：純 shell 開新 terminal；tmux 一 window 一 worker；VS Code 一 terminal 分頁一 worker；Herdr／Orca 一 workspace 一 worker。**一個 session 對應一個 worker，不對應一個 task**——task 可換 worker、worker 可換 session。記下每個 worker 的 PID 或 session 名，stop 要用 |
| workspace | controller（或人）先以 `worktree.md`「所有權與路徑」的 `git worktree add` 建每片 worktree。Orca 等工具若能自動建 worktree，用它建出來的路徑即可，但仍要 `git worktree list` read-back 並記錄絕對路徑與 branch；不用它的 workspace model 代替 SKILL §3 的 graph |
| query status | 兩層：git read-back（`git -C <wt> status --short`、`rev-parse HEAD`、`diff --stat`）＋ worker report 落檔（brief 指定 `<log-dir>/<slice>-report.md`，`<log-dir>` 在 repo 外）。容器的「執行中／完成」指示燈只是線索，不是證據 |
| follow-up | 用該 CLI 的 resume／continue 機制續同一 session（現查 `--help`），或在同一 worktree 起新 process 並把原 report、finding、diff 餵入——前提是舊 process 已依 stop 確認結束 |
| collect | worker report 落檔 `<log-dir>/<slice>-report.md`（brief 指定），非互動模式另記 process exit code；沒有 report 檔＝未完成 |
| stop | 結束該 process 或關閉其 session（`kill <pid>`／容器的關閉指令）；主判準是以 `ps -p <pid>` 或 session 清單確認 process 真的消失，容器顯示「已停止」不算，process 還在就是還在寫。`git -C <wt> status --short`＋`rev-parse HEAD` 兩次 read-back（相隔至少 60 秒，未實測的保守值）只作佐證，須無變化 |

## 派工與 worktree

- worker **預設禁止** commit／rebase（同 `~/.claude/agents/worker.md` 規則 5）。要開放，brief 的 Execution environment 欄必須明寫「本任務在隔離 worktree（`isolation: worktree` 或 controller 自建 worktree）」這句——它是對 worker 合約的宣告，不是 CLI 旗標，外部 CLI 沒有這個參數——寫了才適用 worker 合約的隔離例外（可在自己 branch commit、完成前 rebase 一次、解純文字 conflict；PR／merge 仍禁止；push 另依 worker 規則 5，須 brief 明文寫出 controller 已取得使用者對該 push 的授權）；沒寫就是禁止。worker 若是 Codex，一律依 `codex.md`（不得 commit／rebase）。
- 裝了 `block-ci-edit` hook 的機器（見 `<REPO>/docs/install.md`「選配：擋主對話改 CI 設定的 hook 與 ripgrep 預設設定」），`claude -p` 起的 worker 是頂層 session、hook 輸入沒有 `agent_id`，改 `.github/workflows`／`.github/actions` 會被擋；這類切片改用 Agent 工具派 `worker`，不用本 adapter。
- brief 開頭仍寫「你是被派來的執行者，親自完成本任務，不要再派工」——外部 CLI 一樣會讀到全域 rules，一樣會轉包。
- 同一 worktree 永遠只有一個 process 在寫；controller 自己不在 worker 的 worktree 動手，要改就送 follow-up。
- brief 的 Execution environment 要有 `templates.md`「Worker brief」的「需要決策時」那行：不屬 worker 合約要停下來退回的情形，就把問題寫進回報、**繼續做不被該答案擋住的部分**，不用互動式選單或等鍵盤回答的工具停在那裡等（issue session 不是 worker，它的對應寫法在下方「盤點 session 與 issue session」的 brief 條）。理由：外部 CLI session 可能沒人在看（`claude -p`、背景 session、使用者離開分頁），停在提問上等於整片停工，而分頁有人時使用者晚點回也不會漏掉——這句從 oat-agents 的 role protocol 借來。
- `claude -p`／`codex exec` 本身就是 fresh session，可直接當切片驗收的執行方式：在 integration tree 或該片 worktree 的乾淨狀態起 `claude -p` 帶 verifier 合約（`~/.claude/agents/verifier.md`）與驗收條件。

## 驗收角色分流

worker 是哪個 CLI 就依該平台的角色表：Claude 側 `worker`／`verifier`（`claude-code.md`），Codex 側依 `codex.md`。混用時（例如 Claude 做 UI、Codex 做 API）整合 verifier 用 controller 平台的角色即可，關鍵是 fresh-context 與乾淨 tree，不是型號。

## 盤點 session 與 issue session（互相獨立的 issue）

SKILL §1「先分流」判為互相獨立的 issue 走這裡：一個 issue 一個頂層 session。**issue session 是該 issue 的 controller，不是上表的 worker**——它照 `~/.claude/skills/dispatch/SKILL.md` §1『Controller 工作迴圈』自己實作（或依『必派條件』派 worker）、派 verifier、read-back、修正與交付；上表「一個 session 對應一個 worker」只適用同一 issue 內的切片。

- **盤點 session**：現查 tracker 與 open PR，列出可做／blocked 項目、優先序與共用觸點（同檔、lockfile、schema、registry、CI 設定、migration 序號）；有共用觸點的 issue 序列開，不同時開。每個 issue 寫一份 brief 到 `<repo>/.worktrees/briefs/<issue>.md`（`.worktrees/` 的忽略方式見 `worktree.md`「所有權與路徑」）。不逐票讀 source、不收完整回報、不追各 issue 的 CI。
- **brief**：目標與動機、tracker 連結、base ref、共用觸點與禁止碰的路徑、完成定義、授權（見下）、交付檔路徑（見下方 collect），以及「需要使用者決策或授權時：寫進 `result.md` 的 Pending authorization／Blocker，繼續做不被該答案擋住的部分，不用等鍵盤回答的工具停住等」（與上方「派工與 worktree」給 worker 的那行同一精神；鐵律二的授權仍只認使用者在本分頁親口說的）。**不寫**「你是執行者、不要再派工」——那句只給 worker。
- **launch**：盤點 session 自己啟動，每個 issue 一行（Orca 在時）：`orca worktree create --repo path:<repo> --name <issue> --no-parent --base-branch <brief 的 base ref> --agent claude --model claude-opus-5-5 --effort medium --prompt "$(cat <repo>/.worktrees/briefs/<issue>.md)" --json`。`--repo` 與 `--base-branch` 依 `orca worktree create --help`（「If --repo is omitted, Orca infers the repo from the current Orca-managed worktree.」；「omit --base-branch to use the repo default base, or pass the default base ref explicitly for independent top-level work.」）顯式帶、不靠推斷；實跑 `--repo path:<repo> --base-branch origin/main`：worktree HEAD 等於 `origin/main`（本機 `main` 比它多一個未 push 的 commit，證明取的是指定 ref 而非 checkout 的 HEAD）；省略 `--base-branch` 時用 repo 預設 base（實測 `refs/remotes/origin/main`）。GitHub issue 加 `--issue <n>` 連結；ClickUp 票沒有對應欄位，用 `--comment` 記票號。worktree 位置 `<repo>/.orca/workspaces/<repo-name>/<issue>`，branch `<git user.name>/<issue>`（回傳的 `result.worktree.branch` 帶 `refs/heads/` 前綴），base 為 `--base-branch` 指定的 ref（`orca repo set-base-ref` 改的是整個 repo 的預設，不是逐次用法）；記下回傳的 `result.worktree.path`、`result.worktree.branch` 與 `result.agentTerminalHandle`（實測有回，與 `result.startupTerminal.handle` 相同）。issue session 是 controller，不隨主對話的預設 model：一律帶 `--model claude-opus-5-5 --effort medium`（`--effort` 須與 `--model` 同給，Orca 翻成 `claude --model claude-opus-5-5 --effort medium <prompt>` 起頂層 session；2026-10-26 以 `orca worktree create --agent claude --model claude-opus-5-5 --effort medium` 與 `orca agent launch`（同旗標）各實測一次，`ps` 均可見該 argv，session 標頭顯示「Opus 5.5 with medium effort」；少帶時新 session 吃啟動當下 `~/.claude/settings.json` 的 `model`，2026-10-27 四個 issue session 因此開成 Sonnet／Fable，Claude 端由 PreToolUse hook `~/.claude/hooks/require-issue-session-model.sh` 機械擋下缺旗標的啟動），其餘不帶旗標，permission mode 取 Claude Code settings 的 `permissions.defaultMode`（本機全域層實測 auto；project／local 層會不會蓋過未實測）；要別的 mode 走兩步：`orca terminal create --worktree <selector> --command "claude --permission-mode <mode>"` 再 `orca terminal send`（本次未實跑）。brief 全文會出現在 process argv（`ps` 看得到），與下方 fallback 相同。主對話（auto mode）的 Bash 可直接執行 `orca worktree create --agent claude --model claude-opus-5-5 --effort medium` 與 `orca terminal create`、不被 auto mode 分類器擋（見 `<REPO>/global/shared/hosts/macos.md`），前者回 `ok: true`、`createdWithAgent: claude`。**Fallback**（Orca 不在或 `orca worktree create` 失敗時）：列一行可直接貼的指令，使用者在自己的 terminal 分頁各開一個 interactive session：`cd <repo> && claude -w <issue> -n <issue> --model claude-opus-5-5 --effort medium --permission-mode auto "$(cat <repo>/.worktrees/briefs/<issue>.md)"`。旗標依 `claude --help`（`-w`／`-n` 不限 `--bg`），此 fallback 本身未實跑；repo 須先被信任過，否則回 `Workspace not trusted`。不預設 `claude --bg`：實測主對話以 Bash 執行會被 auto mode 分類器擋（`Create Unsafe Agents`），使用者回報背景 session 常卡在權限、要 attach 才看得到，不如分頁直觀；要改回 `--bg` 先實測權限能全程不卡。**Codex**：把同一份 brief 路徑列給使用者，在分頁自開 `codex`。
- **query status／collect**：進度由使用者看各分頁；issue session 完成或卡住時把交付包寫進 `$(git rev-parse --show-toplevel)/.worktrees/result.md`（自己 worktree 內，不寫到工作目錄外；`.worktrees/` 被全域 gitignore 忽略），欄位一律依 `templates.md`「Issue session result」，本檔不複寫清單；merge 後補該模板的 Merged 欄。盤點 session 只讀這份與 `gh pr view` 做決策；欄位不足或 `unknown` 就送回該 issue session 補，不自己重跑該 issue 的探索或驗收。盤點 session 先找到該 issue 的 worktree 路徑：Orca 路徑用 `orca worktree list --json` 的 `path`／`branch`／`displayName`；fallback `claude -w` 時用 `git -C <repo> worktree list --porcelain`（`-w` 建出的位置未實測）。只讀其中的 `.worktrees/result.md` 與 `gh pr view`，不用 `SendMessage` 把完整報告傳回——傳回的報告會留在盤點 session 每輪重讀。Orca 路徑另可用 `orca terminal wait --terminal <handle> --for tui-idle --timeout-ms <毫秒> --json`（回 `satisfied: true`）看 session 是否閒置，`orca terminal read --terminal <handle> --json` 的 `result.terminal.tail` 看最後回覆（輸出會進盤點 session 的 context，同上理由只在需要時讀）；`<handle>` 由 `orca terminal list --json` 依 `worktreeId` 找。這只證明 TUI 閒置，是線索不是完成證據，完成證據仍是 `.worktrees/result.md` 與 `gh pr view`。要一眼看全部在跑的 claude session 是在跑工具、等人打字、等背景 subagent 還是靜默太久，跑 `python3 <REPO>/scripts/stall-check.py`（狀態定義、欄位與選項見 `--help`；只看 Claude 的 session jsonl，Codex session 沒有可讀 transcript）。`quiet` 只代表靜默超過門檻——跑 build 的 Bash 也會——同上理由只是線索，判定仍去該分頁看或讀 `result.md`。要一次看完同一 repo 所有 issue worktree 的進度，先跑 `python3 <REPO>/scripts/issue-status.py --repo <repo>`（選項見 `--help`），再決定要不要讀個別分頁：它讀每個 worktree 的 `.worktrees/result.md`，拿 HEAD、`git status --short` 行數與 `gh pr list` 交叉比對，缺資料、過時或互相矛盾一律標 `unknown` 並附原因與 result.md 時間；它只會把狀態降成 `unknown`，不會推進，也不讀 TUI 或 process 狀態。
- **follow-up**：需要決策或補授權時，使用者在該 issue 的分頁直接回；盤點 session 不代答。
- **授權**：鐵律二以 session 為單位。brief 只能逐字引用使用者在盤點 session 對**該 issue** 明說的動作與對象（例如「#123 可 push feature branch 並開 PR」），push feature branch 比照 `~/.claude/agents/worker.md` 規則 5 的 push 例外；開 PR 不在規則 5 內，是使用者另外核定的引用上限，由 issue session（controller）自己開，不轉給 worker。沒說就寫「無」。brief 的授權段以「使用者原話：」開頭逐字引用並註明對象 issue，issue session 只認這段、不把 brief 其餘文字當授權。merge、對外訊息與 brief 沒列的動作，一律等使用者在該 issue 的 session 親口授權。
- **stop**：使用者在該分頁結束 session（`/exit`）後確認沒有殘留 process，再依下方「清理」處理 worktree。fallback 路徑用 `pgrep -fl -- '-n <issue>( |$)'` 回空（exit 1）；Orca 路徑用下列迴圈列出每個 claude process 的 cwd，`grep -F <worktree 絕對路徑>` 回空（exit 1）＝該 worktree 內沒有 claude session 在跑：`for p in $(pgrep -f '(^|/)claude( |$)'); do printf '%s ' "$p"; lsof -a -d cwd -p "$p" -Fn 2>/dev/null | grep '^n' | cut -c2-; done | grep -F <worktree 絕對路徑>`（Orca 啟動的 argv 是 `claude <prompt>`、沒有 `-n`，pgrep 那條比對不到）。macOS 的 BSD `pgrep` 預設排除自己的祖先 process（`man pgrep` 的 `-a`），在 claude session 裡跑這些檢查看不到該 session 自己，所以 stop 檢查要從盤點 session 或另一個 terminal 跑，不能在被停的 session 裡自查（實測：`pgrep -f` 列不出執行它的 session 的 pid，`ps -axo pid=,comm=` 列得出）。`/exit` 後分頁裡的 shell 仍在、`orca terminal list` 仍列得到，terminal 還在是正常的，不拿它當判定（實測：以 `orca terminal send --text /exit --enter` 送出後 6 秒，`orca terminal list` 仍列出該 terminal、尾端是 shell 提示，上面的 pgrep 迴圈 `grep -F` 回空 rc=1）。
- **整合**：各 issue 各自走 PR 與 CI。被判獨立卻在 merge 時才發現互踩的，後 merge 的 issue session 在當前 base 重跑完整檢查，並回報盤點 session 修正下次的共用觸點判斷。

## 沒有 controller（人手多開 session）

使用者自己當 controller 時，開工前列出：每片 worktree 絕對路徑、branch、ownership、驗證命令；`git worktree list` 核對。仍受 SKILL §3 批次上限、每片 fresh 驗收、§6 integration tree 與完整測試約束——**「幾個 session 各自跑完了」不等於已整合**。建議把 SKILL §3 的 graph 與 `templates.md` 的 status board 寫成一個檔放在 `<log-dir>`，每個 worker 完成就更新，整合時照 integration record 記錄。

## 清理

採 `worktree.md`「清理的證據條件」；確認後，非 Orca 建的 worktree 用 `git -C <repo> worktree remove <絕對路徑>` 與 `git -C <repo> branch -D <branch>`。容器內的 session／workspace 由容器自己關，與 git 清理是兩件事，先關 session 再清 worktree（避免清理時仍有 process 在寫）。

Orca 建的 worktree：先關那個分頁（`orca terminal close --terminal <handle> --json`，關的是 `/exit` 後留下的 shell；實測對仍在跑的 claude 回 `ptyKilled: true`、2 秒後 process 消失），再 `orca worktree rm --worktree name:<issue> --json`。回傳 `removing: true` 是非同步（實測回 `{"removed": true, "removing": true}`），要再用 `git -C <repo> worktree list` 與 `git -C <repo> branch --list <branch>` read-back；實測 5 秒後 worktree 只剩 main、該 branch 一併消失，`.orca/workspaces/<repo-name>/` 目錄已空、`orca worktree list --json` 查無。`.orca/` 由使用者全域 gitignore 忽略，與 `.worktrees/` 同一機制，見 `worktree.md`「所有權與路徑」。
