# 起 issue session：Orca、純 shell、tmux、VS Code 分頁

配合 [../SKILL.md](../SKILL.md) §2「多個 issue：一 issue 一頂層 session」使用；容器要提供的五個動作與換容器要動的檔見 [container.md](container.md)。issue session 是一個獨立的 coding agent CLI process（`claude` 或 `codex`），在自己的 worktree 裡當該 issue 的 controller；Orca、tmux、VS Code 分頁只是 process 的容器，提供的 workspace、分頁、狀態面板都是 UX，不進任何判斷。盤點 session 要做的只有 launch、query status／collect、stop 三件事，follow-up 由使用者在該分頁直接回。

## 盤點 session 與 issue session

- **brief**：欄位見 SKILL §2；寫到 `<repo>/.worktrees/briefs/<issue>.md`（`.worktrees/` 的忽略方式見 `worktree.md`「所有權與路徑」）。**不寫**「你是執行者、不要再派工」——issue session 是 controller，自己實作、自己派 verifier；需要決策或授權時寫進 `result.md` 繼續做不被擋的部分，不用等鍵盤回答的工具停住等（外部 CLI session 可能沒人在看，停在提問上等於整個 issue 停工；這句從 oat-agents 的 role protocol 借來）。
- **launch**：盤點 session 自己啟動，每個 issue 一行（Orca 在時）：`orca worktree create --repo path:<repo> --name <issue> --parent-worktree path:<repo> --base-branch <brief 的 base ref> --agent claude --model claude-opus-5-5 --effort medium --prompt "$(cat <repo>/.worktrees/briefs/<issue>.md)" --json`。`--parent-worktree path:<repo>` 讓 issue session 在 sidebar 縮在該 repo 主 workspace 的「N children」chip 下（2026-11-07 實跑：回傳 `result.worktree.parentWorktreeId` 等於主 checkout 的 worktree id；只影響 sidebar 分組與「Sleep／Delete with Descendants」選單，git lineage、base ref 都不變），不想分組才用 `--no-parent`，兩者擇一。不用 sidebar 的「Delete with Descendants」清 issue worktree，清理仍走 SKILL §3 的閘門。`--repo` 與 `--base-branch` 依 `orca worktree create --help`（「If --repo is omitted, Orca infers the repo from the current Orca-managed worktree.」；「omit --base-branch to use the repo default base, or pass the default base ref explicitly for independent top-level work.」）顯式帶、不靠推斷；實跑 `--repo path:<repo> --base-branch origin/main`：worktree HEAD 等於 `origin/main`（本機 `main` 比它多一個未 push 的 commit，證明取的是指定 ref 而非 checkout 的 HEAD）；省略 `--base-branch` 時用 repo 預設 base（實測 `refs/remotes/origin/main`）。GitHub issue 加 `--issue <n>` 連結；ClickUp 票沒有對應欄位，用 `--comment` 記票號。worktree 位置 `<repo>/.orca/workspaces/<repo-name>/<issue>`，branch `<git user.name>/<issue>`（回傳的 `result.worktree.branch` 帶 `refs/heads/` 前綴），base 為 `--base-branch` 指定的 ref（`orca repo set-base-ref` 改的是整個 repo 的預設，不是逐次用法）；記下回傳的 `result.worktree.path`、`result.worktree.branch` 與 `result.agentTerminalHandle`（實測有回，與 `result.startupTerminal.handle` 相同）。issue session 是 controller，不隨主對話的預設 model：一律帶 `--model claude-opus-5-5 --effort medium`（`--effort` 須與 `--model` 同給；2026-10-26 實測 Orca 翻成 `claude --model claude-opus-5-5 --effort medium <prompt>` 起頂層 session：以 `orca worktree create --agent claude --model claude-opus-5-5 --effort medium` 與 `orca agent launch`（同旗標）各實測一次，`ps` 均可見該 argv，session 標頭顯示「Opus 5.5 with medium effort」；少帶時新 session 吃啟動當下 `~/.claude/settings.json` 的 `model`，2026-10-27 四個 issue session 因此開成 Sonnet／Fable，Claude 端由 PreToolUse hook `~/.claude/hooks/require-issue-session-model.sh` 機械擋下缺旗標的啟動）。使用者在盤點 session 點名某個 issue 用 Fable 時，該 issue 照樣帶 `--model`／`--effort`，只把 model 換成 `claude-fable-5-2`，其餘 issue 與預設不變；hook 只檢查旗標有沒有帶值、不檢查值，不必改 hook。其餘不帶旗標，permission mode 取 Claude Code settings 的 `permissions.defaultMode`（本機全域層實測 auto；project／local 層會不會蓋過未實測）；要別的 mode 走兩步：`orca terminal create --worktree <selector> --command "claude --permission-mode <mode>"` 再 `orca terminal send`（本次未實跑）。brief 在不在 process argv，2026-10-26 與 2026-11-08（Orca 1.4.253）兩次實測結果不同，不拿 `ps` 判斷 brief 有沒有送到：2026-10-26 實測 argv 尾端帶 prompt；2026-11-08 以 Orca 1.4.253 連續起兩個 issue session，兩次都回 `ok: true`，兩個 claude process 的 argv 都只有約 163 字元、不含 brief，看起來是 agent 輸出，或 brief 被擠出預設 120 行的 tail）時不補送，改用 `--screen` 或加大 `--limit` 再看，判不出來就到該分頁看一眼。主對話（auto mode）的 Bash 可直接執行 `orca worktree create --agent claude --model claude-opus-5-5 --effort medium` 與 `orca terminal create`、不被 auto mode 分類器擋（見 `<REPO>/global/shared/hosts/macos.md`），前者回 `ok: true`、`createdWithAgent: claude`。**Fallback**（Orca 不在或 `orca worktree create` 失敗時）：列一行可直接貼的指令，使用者在自己的 terminal 分頁各開一個 interactive session：`cd <repo> && claude -w <issue> -n <issue> --model claude-opus-5-5 --effort medium --permission-mode auto "$(cat <repo>/.worktrees/briefs/<issue>.md)"`。旗標依 `claude --help`（`-w`／`-n` 不限 `--bg`），此 fallback 本身未實跑；repo 須先被信任過，否則回 `Workspace not trusted`。不預設 `claude --bg`：實測主對話以 Bash 執行會被 auto mode 分類器擋（`Create Unsafe Agents`），使用者回報背景 session 常卡在權限、要 attach 才看得到，不如分頁直觀；要改回 `--bg` 先實測權限能全程不卡。**Codex**：把同一份 brief 路徑列給使用者，在分頁自開 `codex`。
- **query status／collect**：進度由使用者看各分頁；issue session 完成或卡住時把交付包寫進 `$(git rev-parse --show-toplevel)/.worktrees/result.md`（自己 worktree 內，不寫到工作目錄外；`.worktrees/` 被全域 gitignore 忽略），欄位一律依 SKILL §2「issue session result」；merge 後補 Merged 欄。盤點 session 只讀這份與 `gh pr view` 做決策；欄位不足或 `unknown` 就送回該 issue session 補，不自己重跑該 issue 的探索或驗收。盤點 session 先找到該 issue 的 worktree 路徑：Orca 路徑用 `orca worktree list --json` 的 `path`／`branch`／`displayName`；fallback `claude -w` 時用 `git -C <repo> worktree list --porcelain`（`-w` 建出的位置未實測）。只讀其中的 `.worktrees/result.md` 與 `gh pr view`，不用 `SendMessage` 把完整報告傳回——傳回的報告會留在盤點 session 每輪重讀。Orca 路徑另可用 `orca terminal wait --terminal <handle> --for tui-idle --timeout-ms <毫秒> --json`（回 `satisfied: true`）看 session 是否閒置，`orca terminal read --terminal <handle> --json` 的 `result.terminal.tail` 看最後回覆（輸出會進盤點 session 的 context，同上理由只在需要時讀）；`<handle>` 由 `orca terminal list --json` 依 `worktreeId` 找。這只證明 TUI 閒置，是線索不是完成證據，完成證據仍是 `.worktrees/result.md` 與 `gh pr view`。要一次看 Orca 上全部 worktree 的 session 狀態，用 `orca worktree ps --json --agent-wait --limit <n>`，一律經 jq 壓成一行一 worktree 再讀：`orca worktree ps --json --agent-wait --limit 20 | jq -c '.result.worktrees[] | {name: .displayName, repo, branch, parent: .parentWorktreeId, status: .workspaceStatus, unread, live: .liveTerminalCount, verdict: .terminalVerdict, agents: [.agents[] | {state, type: .agentType, prog: .programStatus.state, msg: (.programStatus.message // "")}]}'`（2026-11-07 實跑：每個 agent 有 `state` working／done 等、`agentType`、`programStatus.message` 是 agent 自報的一句；原始 JSON 另含每個 agent 完整的 `lastAssistantMessage`，不過濾會整段進 context；`agentWait` 這次全為 null，不拿它判定）。這與 Orca 的 Agents feed、Agent Dashboard 看到的是同一份狀態，同樣只是線索。issue session 可選擇在寫 `result.md` 時順手 `orca worktree set --worktree active --workspace-status <id> --unread --json` 讓看板欄位對上（`working`→`in-progress`，`awaiting verification`／`ready for authorization`→`in-review`，`merged`→`completed`；2026-11-07 實跑 `--workspace-status in-review --unread` 回 `workspaceStatus: in-review`、`isUnread: true`），這是給人看的，盤點 session 不讀它。要一眼看全部在跑的 claude session 是在跑工具、等人打字、等背景 subagent 還是靜默太久，跑 `python3 <REPO>/scripts/stall-check.py`（狀態定義、欄位與選項見 `--help`；只看 Claude 的 session jsonl，Codex session 沒有可讀 transcript；`name` 欄是 `ListAgents`／`SendMessage` 用的 session 名）。要持續盯著當 dashboard，在另一個終端機 pane 跑 `while :; do clear; python3 <REPO>/scripts/stall-check.py; sleep 30; done`，不要在盤點 session 裡定期呼叫 `ListAgents` 或這支腳本——每次輸出都進 context、每輪重讀。`quiet` 只代表靜默超過門檻——跑 build 的 Bash 也會——同上理由只是線索，判定仍去該分頁看或讀 `result.md`。要一次看完同一 repo 所有 issue worktree 的進度，先跑 `python3 <REPO>/scripts/issue-status.py --repo <repo>`（選項見 `--help`），再決定要不要讀個別分頁：它讀每個 worktree 的 `.worktrees/result.md`，拿 HEAD、`git status --short` 行數與 `gh pr list` 交叉比對，缺資料、過時或互相矛盾一律標 `unknown` 並附原因與 result.md 時間；它只會把狀態降成 `unknown`，不會推進，也不讀 TUI 或 process 狀態。
- **follow-up**：需要決策或補授權時，使用者在該 issue 的分頁直接回；盤點 session 不代答。
- **stop**：使用者在該分頁結束 session（`/exit`），或盤點 session 依 SKILL §3「直接清」自己關分頁後，確認沒有殘留 process，再依下方「清理」處理 worktree。fallback 路徑用 `pgrep -fl -- '-n <issue>( |$)'` 回空（exit 1）；Orca 路徑用下列迴圈列出每個 claude process 的 cwd，`grep -F <worktree 絕對路徑>` 回空（exit 1）＝該 worktree 內沒有 claude session 在跑：`for p in $(pgrep -f '(^|/)claude( |$)'); do printf '%s ' "$p"; lsof -a -d cwd -p "$p" -Fn 2>/dev/null | grep '^n' | cut -c2-; done | grep -F <worktree 絕對路徑>`（2026-10-26 實測 Orca 啟動的 argv 沒有 `-n`，pgrep 那條比對不到）。macOS 的 BSD `pgrep` 預設排除自己的祖先 process（`man pgrep` 的 `-a`），在 claude session 裡跑這些檢查看不到該 session 自己，所以 stop 檢查要從盤點 session 或另一個 terminal 跑，不能在被停的 session 裡自查（實測：`pgrep -f` 列不出執行它的 session 的 pid，`ps -axo pid=,comm=` 列得出）。`/exit` 後分頁裡的 shell 仍在、`orca terminal list` 仍列得到，terminal 還在是正常的，不拿它當判定（實測：以 `orca terminal send --text /exit --enter` 送出後 6 秒，`orca terminal list` 仍列出該 terminal、尾端是 shell 提示，上面的 pgrep 迴圈 `grep -F` 回空 rc=1）。

  **閒置判定**（SKILL §3「直接清」第 3 條）由 `<REPO>/scripts/worktree-clean-check.py` 在關分頁前跑。為什麼不用 `orca terminal wait --for tui-idle`：2026-11-06 實測，跑著 `sleep 600` 的 terminal 也回 `satisfied: true`，只有 shell 提示的 terminal 反而逾時，判不出前景指令。為什麼用 pid 排除 claude：實測 claude 的 process 名是版本號（如 `2.1.319`），不是 `claude`。`orca terminal close --all` 會連前景指令一起停（實測 `sleep 600` 消失），所以判定要在關之前。Codex session 不在 `stall-check.py` 的輸出內，它的 process（實測 `codex` 與它起的 `git`）不會被算成閒置，判定不過，等於要先問；真實 session 留下的 daemon（實測看過 `adb`）也會讓判定不過，這是偏保守的方向，回報後由使用者決定；claude 剛轉 `idle` 時短暫存在的 `caffeinate`（實測隨後消失）等一下重跑即可。沒有 `lsof`／`ps` 的機器（Windows）腳本一律回不可清。

裝了 `block-ci-edit` hook 的機器（見 `<REPO>/docs/install.md`「選配：擋主對話改 CI 設定的 hook 與 ripgrep 預設設定」），issue session 是頂層 session、hook 輸入沒有 `agent_id`，改 `.github/workflows`／`.github/actions` 一樣會被擋；依 dispatch skill §3 先把 diff 給使用者取授權。

## 接手 session（同一個工作目錄換新 session）

使用者說「開新 session 繼續」「開新的主 session 繼續」「開新 main session 做」（含「可以開…」這種句型），或主對話 context 到門檻且還有未做的 phase 時用（dispatch skill §6『主對話 context 管理』；這種情況不必等使用者開口，使用者 2026-11-11 明說自動開才不算打擾）。兩種情況都是目前的 session 把新 session 啟動起來；只回一段 prompt 或交接卡路徑不算完成（2026-10-16 至 2026-11-11 的 session 紀錄裡，這類要求至少有 6 次停在交接卡或 prompt、沒有啟動，其中至少 5 次是使用者再說一次「你可以幫我開」才啟動）。使用者明說「給我 prompt」時才只給文字。

- **位置**：接手 session 開在目前 session 所在的同一個 checkout——在主 checkout 就是主 checkout（使用者說的「主 session」「main session」），在 issue worktree 就是同一個 worktree。不建新 worktree，不用 `orca worktree create`：那是上一節的 issue session，`--parent-worktree` 起的是掛在主 workspace 底下的子 session，不是主 session。使用者要新 session 去做另一個獨立 issue 時才走上一節的 launch。
- **context 到門檻自己啟動時**：先做到目前段落結束，等在途 subagent 回報並處理完再啟動（新 session 收不到它們的回報）。剩下的工作全都卡在使用者的決定或授權時不啟動，先在目前的 session 問；啟動之後用一行告訴使用者為什麼換、新分頁在哪。
- **先寫交接卡**：依 `~/.claude/skills/handoff/SKILL.md` §4『session 交接卡』存好（Codex：`<REPO>/global/shared/skills/handoff/SKILL.md`），記下檔案絕對路徑。
- **launch**（Orca 在時）：`orca agent launch --agent claude --worktree path:<目前 checkout 絕對路徑> --model claude-opus-5-5 --effort medium --surface terminal --focus --prompt "<接手提示>" --json`。`--model`／`--effort` 與 issue session 同值、同樣必帶（缺了會被 `require-issue-session-model.sh` 擋，它也比對 `orca agent launch`）；使用者點名別的 model 時只換值。`--surface terminal` 固定起 CLI，不隨 Orca 的 Chat | CLI 設定；`--focus` 把分頁切到前景，不帶時分頁在背景開（兩者依 `orca agent launch --help`）。接手提示寫三件事：交接卡絕對路徑、下一步的一句話、「授權不延續，需要時重新問使用者」（全域邊界 3，授權以 session 為單位）。成功時回 `ok: true`、`result.outcome.kind` 為 `terminal`、`result.outcome.handle` 是新分頁的 terminal handle（2026-11-05 至 2026-11-10 在主 checkout 與 issue worktree 都實跑過，`result.receipt.detail` 回 `Started a terminal agent, as requested.`）。
- **read-back**：同上一節 launch 的規則，`orca terminal read --terminal <handle> --json` 的 `result.terminal.tail` 出現接手提示的第一行＝已送到；只有空提示時隔 10 秒再讀，兩次都空才用 `orca terminal send` 補送。handle 沒取到時用 `orca terminal list --worktree path:<目前 checkout 絕對路徑> --json` 找最新的一個。該路徑第一次開 Claude 時 session 可能停在信任資料夾的對話框（2026-11-06 起 issue session 時遇過一次），read-back 看到就請使用者到分頁回答。
- **啟動之後**：告訴使用者新分頁的標題或 handle、請他到那個分頁繼續；目前的 session 不再寫這個 working tree（全域邊界 5），也不自己關分頁。
- **Fallback**（Orca 不在或 launch 失敗）：列一行可直接貼的指令 `cd <目前 checkout 絕對路徑> && claude --model claude-opus-5-5 --effort medium "<接手提示>"`，並明說新 session 沒有啟動。此 fallback 本身未實跑。
- **Codex**：`orca agent launch --help` 的範例有 `--agent codex`，本制度未實跑；實跑前照 Fallback 的做法，把交接卡路徑列給使用者在分頁自開 `codex`。

## 沒有盤點 session（人手多開分頁）

使用者自己當盤點者時，開工前列出：每個 issue 的 worktree 絕對路徑、branch、base SHA；`git worktree list` 核對。每個 issue 仍各自 fresh 驗收、各自走 PR 與 CI——**「幾個分頁各自跑完了」不等於已 merge**，各 issue 的 `.worktrees/result.md` 就是 status board。

## 清理

採 `worktree.md`「清理的證據條件」；確認後，非 Orca 建的 worktree 用 `git -C <repo> worktree remove <絕對路徑>` 與 `git -C <repo> branch -D <branch>`。容器內的 session／workspace 由容器自己關，與 git 清理是兩件事，先關 session 再清 worktree（避免清理時仍有 process 在寫）。使用者自己開的分頁（fallback `claude -w`、Codex）盤點 session 關不了：session 還在就保留並回報，請使用者 `/exit`。

直接清（SKILL §3）不分容器，都先做這兩步，成功才往下：

1. `python3 <REPO>/scripts/worktree-clean-check.py --repo <repo> --worktree <wt>`，exit 0 才繼續。
2. 讀 `<wt>/.worktrees/result.md`，把後續事項帶進下一個相關 brief 或 handoff；檔案隨 worktree 一起刪。使用者明確授權清、且 worktree 沒有 `result.md` 時略過這兩步，改核對 `worktree.md`「清理的證據條件」第 2 條。

Orca 建的 worktree 依序做：

1. 做完上面兩步（授權清另依上面）；條件 1 的 process 檢查在第 3 步。
2. 關該 worktree 的所有 terminal：`orca terminal close --worktree path:<wt> --all --json`。同一 worktree 常有多個 terminal（實測 3 個一次關完，回 `closed: 3`、`stopped: 3`）；逐個關用 `--terminal <handle>`，實測對仍在跑的 claude 回 `ptyKilled: true`、2 秒後 process 消失。
3. 跑「stop」的 process 檢查，回空且 `git -C <wt> status --short` 仍為空才往下。
4. `orca worktree rm --worktree path:<wt> --delete-branch --json`。selector 用 `path:`：`orca worktree rm` 沒有 `--repo`，多 repo issue 的同名 worktree 用 `name:<issue>` 會有歧義（`orca terminal list --worktree name:main` 實測回 `selector_ambiguous`；`orca worktree rm` 沒有對歧義名實跑）。不帶 `--force`：工作區有改動時實測回 `ok: false`，不刪。
5. read-back：`git -C <repo> worktree list` 與 `git -C <repo> branch --list <branch>`。回傳可能帶 `removing: true`（非同步，曾實測回 `{"removed": true, "removing": true}`），等幾秒再查。不帶 `--delete-branch` 時 branch 會留著（2026-11-06 實測）。帶了之後，Orca 證得出已合併就刪（實測內容相同、SHA 不同的 branch 被刪），證不出就回 `preservedBranch` 並保留（實測 base 上沒有的 commit）；第 1 步已核對內容在 base 上時，用 `git -C <repo> branch -D <branch>` 刪。`.orca/` 由使用者全域 gitignore 忽略，與 `.worktrees/` 同一機制，見 `worktree.md`「所有權與路徑」。

使用者說「做完」時（SKILL §3），worktree 清完再做這兩項，其中一項做不到不影響另一項，回報原因：

- **關 issue**：多 repo issue 等每個 worktree 都判定過才做。`Issue` 欄是 GitHub issue 時，先 `gh issue view <n> -R <owner/repo> --json state`，`OPEN` 才 `gh issue close <n> -R <owner/repo>`（PR 可能已自動關掉）。其他 tracker 用該 tracker 的工具改狀態；對應不到就不動，回報一行寫「未動」與原因。
- **匿名 docker volume**：`docker ps -a --filter label=com.docker.compose.project --format '{{.ID}} {{.State}} {{.Label "com.docker.compose.project.working_dir"}}'`，只處理 working_dir 等於 `<wt>` 或在 `<wt>/` 底下、狀態是 `exited` 或 `created` 的 container，逐個 `docker rm -v <id>`；匿名 volume 被 container 佔用時 `docker volume rm` 回 `volume is in use`，所以連已停止的 container 一起刪（2026-11-09 實測 Docker 29.9.2：compose 建的 container，`docker rm -v` 刪掉匿名 volume，具名 volume 留著；`docker compose down` 不帶 `-v` 時匿名 volume 留著）。不加 `-f`，還在跑的 container 不動，回報。沒有這個 label 的 container（`docker run` 起的）與已經沒有 container 的 volume，證明不了屬於該 session，不刪，回報。
