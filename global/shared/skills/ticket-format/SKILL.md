# ticket-format — 票的固定格式

> 讀者：要開 ClickUp 票或 GitHub issue、或要改既有票描述的 agent。目的是讓讀票的人與寫 brief 的人一眼找到判定依據，並讓票不隨時間過期。

repo 有自己的 issue 範本（`.github/ISSUE_TEMPLATE/`）或專案 `CLAUDE.md`／`AGENTS.md` 規定票的格式時，以專案為準；沒有才用本格式。

## 1. 描述的段落

段落標題逐字照抄，只用這一套中文標題，不另出英文版；段落順序固定，沒內容的選填段整段省略。

```markdown
## 要做什麼
這張票讓哪個行為能動，從使用者或呼叫端的角度寫。不列各層怎麼改。

## 驗收條件
- [ ] 另一個人只憑這句就能判定過或不過

## 不含
（有容易被順手做掉的相鄰範圍才寫）

## 重現步驟
（選填；bug 票才寫）

## 設計稿
（選填；有設計稿或素材來源才寫）

## 待決
（選填；開票時還沒定、會影響要做什麼或驗收條件的問題）

## 完成後回報
（選填；交給別的團隊做、需要對方回填資訊時才寫）

## 子票順序
（選填；母票才寫，子票之間沒有硬依賴但有建議先後時）

## 背景
（選填；給人看的票才寫，三行內；帶日期的現況不寫進票，寫留言）
```

- **要做什麼**：寫完成後誰能做到什麼、系統對什麼輸入有什麼反應；已定的決定（例如「`state` 不符一律登入失敗」）寫在這裡。不寫「改 A 層、再改 B 層」的施工清單，那是做的人開工後自己決定的。
- **驗收條件**：每條各自可判定；判不了的句子（「流程順暢」「符合設計」）改寫成看得到的結果。
- **不含**：只列相鄰、容易被順手做掉的範圍；沒有就省略，不寫「無」。
- **重現步驟**：照做就能看到問題的最少步驟，加上預期結果與實際結果。重現用的指令可以寫成程式碼區塊，這是 §2 規則 3 的例外；當下的版本、環境寫進步驟，之後的調查結果寫留言。
- **設計稿**：設計稿節點或素材來源的連結清單，每條一行、附畫面或素材名稱；畫面規格寫在要做什麼與驗收條件，不寫在這裡。
- **待決**：每條一個問題，寫出誰來決定；定案後照 §2 規則 4 的待決例外處理。
- **完成後回報**：列出要對方回填的資訊（網域、ID、設定值的位置），每條一行；對方怎麼做不寫在這裡。
- **子票順序**：子票照建議先後編號列出、各附一句為什麼排這裡；有硬依賴的仍設成原生依賴（§2 規則 2），這段只補原生欄位表達不了的建議順序。
- **背景**：選填，三行內，只寫讀票的人需要的「為什麼要做」。

## 2. 配套規則

1. **驗收只有「驗收條件」一段**：不另寫「完成定義」「Done when」「驗收」之類的段落；要求附證據（截圖、指令輸出）就寫進對應那條驗收條件。
2. **依賴與母子關係用 tracker 原生欄位**：先後順序設成依賴（blocking／waiting on），子票掛在母票底下（GitHub 用 sub-issue），描述裡不再列「前置」「子票」「相關票」清單。tracker 沒有對應欄位時才寫成一行文字。例外是母票的「子票順序」段：原生欄位表達不了的建議先後寫在那裡。
3. **不寫檔案路徑、行號、程式碼片段**：它們很快過期。例外是比文字更精確表達決定的 schema 或型別形狀（狀態機、欄位型別、設定的形狀），只留表達決定的部分，不貼可執行的整段程式；另一個例外是「重現步驟」段的重現指令。
4. **之後的變動寫留言，不重寫描述**：進度、現況、實測結果、PR 連結、「某項已完成」一律寫留言。只有決定改變了「要做什麼／驗收條件／不含」時才改描述，只改那一段、其餘段落原樣保留，並在留言寫改了什麼與原因。例外是「待決」段的條目定案：刪掉該條，結論改變了上述三段之一時一併改那一段，留言記結論；結論是維持原樣時只刪該條。

## 3. 舊段落名的去處

本表只用在兩種情形：開新票時手上的草稿用了舊段落名，或改既有舊格式票時被改到的那一段要放到哪個新段落。改既有票不因此整份重排，沒改到的舊段落照 §2 規則 4 原樣保留。不在表上的段落不要自己新增，照 §1 各段的意思判斷去處。

| 舊段落 | 去處 |
|---|---|
| 目標、需求、範圍、要做的事 | 要做什麼（施工步驟拿掉，只留行為與決定） |
| 完成定義、Done when、驗收 | 驗收條件 |
| 不做、不在這張票 | 不含 |
| 前置、時機、子票、相關、硬依賴的先後 | tracker 原生的依賴與母子欄位 |
| 子票與建議順序、非硬依賴的建議先後 | 子票掛原生母子欄位，建議先後寫子票順序 |
| 設計稿、來源（素材連結） | 設計稿 |
| 待釐清、待討論、實作前要定的事 | 待決 |
| 重現、實測（開票當下的重現指令與結果） | 重現步驟；開票後的實測結果寫留言 |
| 完成後請回報 | 完成後回報 |
| Priority 的意思 | 不寫進票，放 list 或 space 的說明 |
| 現況（帶日期）、進度、PR 與版本 | 留言 |
| Why、背景 | 背景（三行內），或併進要做什麼 |

## 4. 邊界

- PR 標題與內文：`create-pr` skill。
- 把票轉成派工 brief：`handoff` skill 的 brief 卡；brief 的驗收條件從本票的「驗收條件」段照抄。
- README、設計說明、wiki 頁等長存文件：`writing-principles` skill。
- commit message：`git-commit` skill。
