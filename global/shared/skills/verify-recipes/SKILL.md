# verify-recipes — 使用者視角的驗證食譜

> 讀者：被使用者叫來替某個 repo 寫或更新驗證食譜的 session，語言不限。

驗收一個專案的改動時，驗收者常要自己摸索「這個功能怎麼走到、用什麼驅動、看到什麼算過」，每次重寫探針。食譜把這些答案寫成一份放在專案裡的文件，下一個驗收者照著跑就能判過或不過。

## 食譜是什麼、不是什麼

- 每節是一個**使用者看得到的功能**：終端使用者在畫面上看到的、接入者從公開 API 或發佈產物看到的、CLI 使用者從指令看到的。內部模組、測試類別、重構不是一節。
- **不放實作細節**：不寫類別名、方法名、呼叫鏈、內部檔案路徑或目錄結構。那些會隨重構失準，而且驗收者要的是「從外面怎麼驗」。例外：驅動指令本身需要的名字（build task、CLI 子命令與旗標、adb 指令、applicationId 或 bundle id、log tag）、使用者看得到的輸出文字，以及 PR 要一起改的對外檔案（例如公開 API 的 dump 檔）。
- **每條要實跑過才算**：照文字逐字跑一次、看到「算過」那句描述的結果，才在「驗證紀錄」寫通過。跑不起來的節保留，標 `未實測` 與原因，不刪也不寫成通過。

## 放哪裡

目標 repo 的 `docs/verify-recipes.md`，一個 repo 一份；沒有 `docs/` 就建立。多個可獨立交付的子專案（monorepo）各自放在子專案的 `docs/verify-recipes.md`。

寫進目標 repo 要使用者當次同意；沒同意前寫到暫存目錄，回報路徑讓使用者讀過再決定。

## 每節的固定欄位

標題是功能名，底下五個欄位加一行驗證紀錄，順序固定：

| 欄位 | 寫什麼 |
|---|---|
| 怎麼走到 | 前置條件與要先啟動的東西（裝置、模擬器、後端、帳號、設定值）；不需要的也寫明，例如「不需要後端」 |
| 驅動 | 可直接複製執行的指令或工具操作；用 repo 自己的腳本與文件裡的指令，不另寫一次性探針 |
| 看到什麼算過 | 可判定的輸出或畫面：哪幾行、什麼順序、結束碼、前景是哪個畫面；同時寫什麼情況判不過。另一個 agent 只憑這句就要判得了 |
| 陷阱 | 會讓人誤判的事：裝置狀態、快取、上一輪殘留、看錯報告；每條寫成「現象 → 怎麼分辨或避開」 |
| 驗證紀錄 | `已實測（YYYY-MM-DD，環境）`＋commit＋結果（通過，或判不過與現象），或 `未實測`＋原因；做過反向驗證的另寫反向的結果。兩個固定值與 `writing-principles` 原則 8 相同，食譜是長存參考頁，也照它的其他原則寫 |

多節共用的前置（開模擬器、起後端）寫在最前面一節「共用前置」，各節只寫「做過共用前置」。

## 步驟

1. **列功能**：從使用者看得到的入口找，依序是 README、接入或使用指南（尤其是它的驗證清單）、範例 App 或 CLI 的 `--help`、發佈產物（套件座標、公開 API dump）。不從原始碼目錄樹找功能。先列清單給使用者看一眼範圍再寫，數量不限，CI 已涵蓋的與一般 PR 不跑的都列。
2. **找驅動方式**：用 repo 現成的腳本、build task、範例 App 的自動執行參數；文件寫了指令就照用。沒有現成驅動、只能手動點畫面的，照實寫手動步驟。
3. **建本機 clone**：`git clone --local --no-hardlinks <repo> <暫存目錄>/clone`。build、跑測試、裝 App 都在 clone 裡做，不在使用者的 checkout 裡，因為它們會產生檔案。動手前後各跑一次 `git -C <repo> status --short --ignored`，兩次相同才算沒動到使用者的 checkout。
4. **逐節實跑**：照草稿的文字逐字跑。跑出來和「算過」不符就先判斷是文字寫錯（改文字再跑）還是功能真的壞了（回報使用者，不改食譜去遷就）。把實際看到的輸出行原樣寫進「看到什麼算過」，不憑文件推測輸出長什麼樣。判定句只要求一定會出現的行與一定成立的順序：非同步產生的行（狀態變化、背景回呼）跟其他行的先後不保證，就不寫順序。輸出有非同步成分的節至少跑 3 次，3 次都判過才記通過；判不過的那幾次照實記在驗證紀錄。每次實跑的輸出存檔，「驗證紀錄」引用的每個字串都要能在存檔裡找到，結束碼也要存進檔。
5. **至少一節做反向驗證**：在 clone 裡故意弄壞該功能（改名一個公開宣告、改壞一個設定值），照食譜跑，要看到判不過；改回後再跑一次看到恢復通過。看不到判不過，表示「算過」那句不夠嚴，改寫到能分辨為止。
6. **跑不起來的節**：需要的裝置、後端、帳號或授權不在，就標 `未實測` 並寫原因。需要安裝東西（SDK 元件、系統映像、服務）才能跑時，先問使用者，不自己裝。
7. **掃實作細節**：寫完對食譜跑一次殘留掃描，命中的逐條判斷是不是上面的例外，不是就改寫成使用者看得到的說法：

   ```bash
   # 從原始碼收集型別與函式名（依語言調整 pattern），再到食譜裡找整字命中
   rg --hidden -o --no-filename -r '$1' '\b(?:class|object|interface|enum|struct|protocol|fun|func|def)\s+([A-Za-z_][A-Za-z0-9_]*)' <clone> -g '!**/build/**' | sort -u > <暫存目錄>/identifiers.txt
   rg -n -w -F -f <暫存目錄>/identifiers.txt <食譜檔>
   # 內部檔案路徑
   rg -n 'src/|\.(kt|java|swift|dart|ts|tsx|py|cs|go)\b' <食譜檔>
   ```

   第一條會命中常見英文字（`main`、`init`、`test`），逐條看是不是指程式碼。

## 維護

- 驅動步驟、輸出文字或前置條件改了，同一個 PR 更新該節並重跑，改「驗證紀錄」。
- 新增使用者看得到的功能時加一節；功能移除時刪節。
- 驗收者照食譜跑出和「算過」不符時，先確認陷阱欄列的情況都排除了，再判定功能壞了或食譜過時。

## 範例（虛構）

```markdown
## 3. 匯出報表成 CSV

- **怎麼走到**：不需要後端；`make build` 產生 `./bin/report`。
- **驅動**：`./bin/report export --from 2026-01-01 --to 2026-01-31 --format csv > /tmp/out.csv; echo exit=$?`
- **看到什麼算過**：`exit=0`；`/tmp/out.csv` 第一行逐字是 `date,orders,revenue`，其後 31 行、每行第一欄是 1 月的日期。`exit` 非 0、標題列不同或行數不是 31，判不過。
- **陷阱**：
  - 本機時區不是 UTC 時頭尾兩天會跨日 → 先 `export TZ=UTC` 再跑。
  - 上一次的 `/tmp/out.csv` 還在 → 用 `>` 覆寫，不要用 `>>`。
- **驗證紀錄**：已實測（2026-01-31，macOS 15），commit `abc1234`：通過。反向：把 `--format` 改成不存在的 `xlsx`，`exit=2`、判不過；改回恢復通過。
```

## 不做

- 不畫 code graph、不寫架構說明；那些屬於專案自己的架構文件。
- 不改目標 repo 的程式碼，不自動修壞掉的功能；發現壞了回報使用者。
- 不替食譜裡跑不起來的節編造輸出。
