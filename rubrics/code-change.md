# Rubric — 程式碼變更

> 用途：驗收實作／修 bug／重構類產出的預設判準。機械驗證可由製作者自跑但必須附指令與輸出（見 `<REPO>/rules/20-judgment.md` §2）；本檔是「附了輸出之後還要看什麼」。
> 判定方式：逐條 PASS／FAIL／UNSURE，每個 FAIL 附 `檔案:行號`。

## 1. 執行證據

- 有實際指令輸出（test／build／lint／實跑／schema），不是「邏輯上應該可以」。
- 輸出對應的是**本次改動後**的程式碼，不是舊的 scrollback。
- 主要路徑至少實跑過一次；只有單元測試綠不足以宣稱功能可用。
- **UI／視覺對齊不得只憑 a11y snapshot 判定**：snapshot 不含只有視覺、無文字的元素（進度條、色塊、icon-only），拿它判「新舊版一致」會漏掉純 CSS 的差異。要截圖或用 `browser_evaluate` 抓 computed style。

## 2. 沒有為了通過驗證而作假

- 沒有寫死的期望值、沒有針對測試輸入特化的分支。
- 沒有被關掉、skip 掉或放寬的檢查；若有，必須是派工明確授權的。
- 失敗的測試沒有被改成符合現況的斷言（除非那正是任務目標）。

- **交付的價值要被測試守住**：若這次改動的價值在於某個輸出、訊息、綁定或診斷能力，問「把它拿掉或換成固定值，有任何測試會紅嗎」；答不出來就是沒有交付，測試全綠不算證據（2026-09-12 三片各自抓到：regex 只認變數名不認來源、失敗訊息不說原因、snippet 換固定字串，既有測試都不紅）。

## 3. 風格對齊

- 改動處的命名、註解密度、慣用寫法與**周圍程式碼**一致，不是套用通用偏好。
- 沒有順手夾帶的無關重構或格式化。
- 註解密度以上一條的周圍慣例為上限，內容依 `<REPO>/rules/20-judgment.md` §7：新增註解解釋「為什麼」（難懂處、商業決策），不複述程式碼做什麼；文件不因這次改動被要求同步翻譯，但被改錯的句子要改或刪。
- **規範掃描的對象是改動過的整段 code，不是 diff `^+` 命中的行**：重構過的函式要為它的現況負責，函式內沿用下來的舊違規一樣算數。

## 4. 範圍

- 只動了派工授權的範圍；超出的部分有在回報中明說。
- 新增依賴有在回報中說明理由。
- 重構類任務行為未改變：有前後同一指令的輸出對照。

## 5. 殘留掃描（重構／改名／抽取／工具遷移／**更正事實宣稱**類必查）

- 舊引用、舊字串、舊路徑、舊工具名已用全 repo `rg` 驗證無殘留，並附搜尋指令與輸出（搜尋方法與觸發清單見 `<REPO>/rules/20-judgment.md` §2 補充判準，兩邊一致）。
- **更正一句錯的事實宣稱也是字串替換任務**：同一句錯的話很少只寫過一次，而且第二現場常在**不同類型的檔案**上（例如 spec 之外的 seed 表）——只掃 docs 找不到。
- 搜尋範圍含 entrypoint、設定檔、腳本、`.github/workflows` 與 `.github/actions`——PR CI 測不到的 release／deploy-only 路徑要另外查。

## 6. 新增的檢查／守衛／gate 本身（有新增才查）

本檔其餘各節問的都是「你真的驗過嗎、是不是假的」。這一節問的是相反方向的事：**新加的那個
檢查會不會在不該叫的時候叫**。誤叫比漏叫更快讓一個檢查失去信任——被誤叫過兩次的 gate，
之後真的叫的時候沒有人會看。

- **判定條件對齊被檢查者「實際會走到的分支」**，不是對齊「這個設定看起來不完整」。查法：
  把被檢查的那段 code 的條件抄出來，逐條對照新檢查的條件。
- **守衛的訊號與被守衛的機制獨立**。拿同一個 pattern 去數自己解析出來的筆數＝自己驗自己，
  pattern 一變兩邊一起瞎；恆真的鏡像斷言（逐字重算被測物自己的定義式）同類。
- **比的是該比的子集，不是全集**。守衛拿全集當期望值時，**做對事會被測試擋**（停用一項並
  照規矩移除，守衛反而紅）——這種紅燈會逼下一個人把正確的改動改回去。
- **「什麼都沒驗到」與「全部通過」的輸出不得長得一樣**（量測／檢查工具必查）：把外部依賴
  全部弄成打不到，看它的總結行講什麼。只報「失敗 0」的工具在零命中時讀起來像全過——
  總結要報**成功計數**，缺 positive control 的檢查等於沒有檢查。
- **新檢查若會擋住流程**（exit 1、CI gate、blocking assertion），先確認正式環境當下的實際
  狀態通得過——查法是實查那個環境，不是讀設定檔推論。

## 7. 失敗路徑與不可逆副作用（diff 含外部呼叫、權限請求或不可逆副作用才查）

happy path 的測試與突變只證明「做了的事有做到」。寫 code 的 session 接著寫測試，問不出「沒做到的時候呢」，這一節由 verifier 替它問。對 diff 裡每個外部呼叫（API、平台權限、裝置／金鑰讀寫、本機狀態清除）與不可逆副作用（寫後端狀態、清本機進度或快取、覆寫資料；兩側定義見 `<REPO>/rules/20-judgment.md` §2 判準第 3 點，§7 兩側都查）逐題回答；查過沒問題的題也要寫「查過，沒有」並說查了哪裡。

- **失敗時的呈現**：呼叫失敗或回空時畫面顯示什麼？「沒讀到」不得顯示成 0、空清單或成功。
- **取消與順序**：使用者中途拒絕或取消（權限、確認框）時，前面已做掉的不可逆步驟是什麼？可取消、可能失敗的步驟要排在不可逆步驟之前。
- **重入**：同一入口連按兩次、兩個入口同時觸發會怎樣？缺 in-flight guard 且重複觸發會造成重複副作用（重送、重清、重綁）即 FAIL；重複觸發結果等同一次（idempotent）可 PASS，要寫出為什麼。
- **慢與無回應**：網路慢或不回時哪個畫面卡住？阻塞使用者流程的等待沒有 timeout 或退路即 FAIL；不阻塞 UI 的背景等待可 PASS。
- **狀態訊號**：畫面上每個狀態（已同步、已綁定、最後時間）由哪個訊號推出？「讀到資料」不等於「對方收到」。
- **放寬既有防線的疊加情境**：diff 拿掉或放寬的既有檢查（含先前 review 加的防線），與其他已核准規則疊起來會不會出現沒人討論過的情境？列出交派工者確認，verifier 不自行判定可接受，列出的情境本身不計 FAIL／UNSURE，放在回報的「無關後續事項」區標「需派工者確認」；只有 diff 拿掉了既有檢查，而製作者的交接（worker 回報、PR 說明）完全未提及時才 FAIL。放寬本身另依 `<REPO>/rules/20-judgment.md` §2「改既有檢查／過濾／驗證規則」。
- **跨 repo 行為宣稱**：對另一個 repo（後端、SDK）的行為宣稱要以該 repo 的實作為據，API 文件只算線索。
- **突變要打失敗分支**：§2 的突變檢查若全在成功判定上，等於沒驗這一節；至少一處「拒絕／失敗後不該發生的副作用」改成會發生時要有測試變紅。

## 8. 開放題（必答）

「這個改動最可能在哪個情境炸掉，而現有驗證抓不到？」
