# Rubric — 程式碼變更

> 用途：驗收實作／修 bug／重構類產出的預設判準。機械驗證可由製作者自跑但必須附指令與輸出（見 `~/.claude/rules/10-dispatch.md` §5）；本檔是「附了輸出之後還要看什麼」。
> 判定方式：逐條 PASS／FAIL／UNSURE，每個 FAIL 附 `檔案:行號`。

## 1. 執行證據

- 有實際指令輸出（test／build／lint／實跑／schema），不是「邏輯上應該可以」。
- 輸出對應的是**本次改動後**的程式碼，不是舊的 scrollback。
- 主要路徑至少實跑過一次；只有單元測試綠不足以宣稱功能可用。
- **UI／視覺對齊不得只憑 a11y snapshot 判定**：snapshot 不含只有視覺、無文字的元素（進度條、色塊、icon-only），拿它判「新舊版一致」會漏掉純 CSS 的差異。要截圖或用 `browser_evaluate` 抓 computed style。

## 2. 沒有為了通過驗證而作假

- 沒有寫死的期望值、沒有針對測試輸入特化的分支。
- 沒有被關掉、skip 掉或放寬的檢查；若有，必須是派工明確授權的。
- 失敗的測試沒有被改成符合現況的斷言（除非那正是任務目標）。

## 3. 風格對齊

- 改動處的命名、註解密度、慣用寫法與**周圍程式碼**一致，不是套用通用偏好。
- 沒有順手夾帶的無關重構或格式化。
- **規範掃描的對象是改動過的整段 code，不是 diff `^+` 命中的行**：重構過的函式要為它的現況負責，函式內沿用下來的舊違規一樣算數。

## 4. 範圍

- 只動了派工授權的範圍；超出的部分有在回報中明說。
- 新增依賴有在回報中說明理由。
- 重構類任務行為未改變：有前後同一指令的輸出對照。

## 5. 殘留掃描（重構／改名／抽取／工具遷移／**更正事實宣稱**類必查）

- 舊引用、舊字串、舊路徑、舊工具名已用全 repo `rg` 驗證無殘留，並附搜尋指令與輸出（搜尋方法與觸發清單見 `~/.claude/rules/20-judgment.md` §2 補充判準，兩邊一致）。
- **更正一句錯的事實宣稱也是字串替換任務**：同一句錯的話很少只寫過一次。2026-08-22 一次「某來源的失敗根因」更正，同一句散在 spec 三處＋另一張 seed 表，分兩輪驗收才清完——第二現場在**不同類型的檔案**上，只掃 docs 找不到。
- 搜尋範圍含 entrypoint、設定檔、腳本、`.github/workflows` 與 `.github/actions`——PR CI 測不到的 release／deploy-only 路徑要另外查。

## 6. 新增的檢查／守衛／gate 本身（有新增才查）

本檔其餘各節問的都是「你真的驗過嗎、是不是假的」。這一節問的是相反方向的事：**新加的那個
檢查會不會在不該叫的時候叫**。誤叫比漏叫更快讓一個檢查失去信任——被誤叫過兩次的 gate，
之後真的叫的時候沒有人會看。

- **判定條件對齊被檢查者「實際會走到的分支」**，不是對齊「這個設定看起來不完整」。查法：
  把被檢查的那段 code 的條件抄出來，逐條對照新檢查的條件。
- **守衛的訊號與被守衛的機制獨立**。拿同一個 pattern 去數自己解析出來的筆數＝自己驗自己，
  pattern 一變兩邊一起瞎；恆真的鏡像斷言（逐字重算被測物自己的定義式）同類。
- **比的是該比的子集，不是全集**。守衛拿全集當期望值時，**做對事會被測試擋**（停用一項並
  照規矩移除，守衛反而紅）——這種紅燈會逼下一個人把正確的改動改回去。
- **「什麼都沒驗到」與「全部通過」的輸出不得長得一樣**（量測／檢查工具必查）：把外部依賴
  全部弄成打不到，看它的總結行講什麼。只報「失敗 0」的工具在零命中時讀起來像全過——
  總結要報**成功計數**，缺 positive control 的檢查等於沒有檢查。
- **新檢查若會擋住流程**（exit 1、CI gate、blocking assertion），先確認正式環境當下的實際
  狀態通得過——查法是實查那個環境，不是讀設定檔推論。

## 7. 開放題（必答）

「這個改動最可能在哪個情境炸掉，而現有驗證抓不到？」
